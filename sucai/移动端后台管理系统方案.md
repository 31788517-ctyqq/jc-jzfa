# 移动端后台管理系统方案

> 制定日期：2026-06-12（v2 修订：对照代码实况全面校准）
> 目标：轻量化手机端管理后台，管理员可随时用手机处理核心运营事务，同时兼顾 PC 端使用

---

## 0. 前置条件：分支与代码现状（必读）

本方案依赖的全部认证/管理资产位于 **`local/auth-preview` 分支**，`master` 分支上没有任何 auth 体系文件。开发前必须先明确分支策略。

| `preview/js/pages/admin-referrals.js` | auth-preview 工作区 | **未跟踪（??），未提交** |
| `preview/js/main-fusion.js`（admin 路由注册） | auth-preview 工作区 | 已修改未提交（M） |

### 0.2 关键阻塞问题

1. **`admin-payments.js` / `admin-referrals.js` 当前不可用**：两个页面使用旧版调用签名 `api('/api', { action: 'xxx', token: true, ... })`，而现行 `preview/js/api.js` 的签名是 `api(action, data, retries)`（token 自动从 auth-client 注入 `X-Auth-Token` 请求头）。按旧签名调用时 `'/api'` 会被当作 action 发给后端，无法匹配任何 case，**所有请求必然失败**。移植到统一后台时必须重写全部 API 调用。
2. **auth-preview 与 master 已长期分叉**：master 上有大量 auth-preview 没有的提交（数据管线、页面样式重构等），合并需要专门处理冲突。
3. 本方案所有开发应在 auth-preview 分支（或其延续分支）上进行，**P-1 阶段先收尾提交工作区文件**，合并 master 的时机另行决策。

## 1. 背景与动机

### 1.1 现状问题

| # | 问题 | 影响 |
|:--|------|------|
| 1 | `admin-payments.js` / `admin-referrals.js` 各自独立且 API 调用签名失配 | 页面实际无法工作；且无任何入口（profile 页未渲染管理入口，项目无 hash 路由，只能在控制台手敲 `switchTab('admin-payments')`） |
| 2 | 用户/角色管理 API 已完备（`routes/users.js`），**无前端页面** | 管理员无法在浏览器管理用户账号，只能 curl 操作 |
| 3 | 管理页面使用白色卡片风格（`payments.css` 中 `.admin-*` 类，`#fff` 底 + `#7c3aed` 紫） | 与项目暗色主题（`--bg: #111820`）视觉割裂 |

## 2. 设计目标

1. **单一入口**：管理员只需一个「管理后台」页面（`switchTab('admin')`），内部 Tab 切换
2. **移动优先**：适配 440px 手机宽度，触摸友好（按钮≥44px）
3. **暗色统一**：复用项目 `--bg` / `--card` / `--text` CSS 变量
4. **补缺不重造**：参考现有 admin-payments / admin-referrals 渲染逻辑，但 API 调用按新签名重写；运维操作直接对接已有的 5 个 ops action
5. **权限分层可见**：`super_admin` 全功能；`ops_admin` 可见用户列表（只读）+ 系统运维；写操作按钮按 permission code 动态隐藏
6. **🔴 先堵权限漏洞**：支付/返利 admin action 补权限映射是 P0，先于一切 UI 开发

## 3. 页面架构

### 3.1 整体布局

```
┌─────────────────────────────────────────┐
│  ← 返回个人中心    🔧 管理后台           │  ← 深色顶栏
├─────────────────────────────────────────┤
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐  │
│  │ 👥   │ │ 💎   │ │ 💰   │ │ ⚙️   │  │  ← Tab 切换栏
│  │ 用户 │ │ 订阅 │ │ 返利 │ │ 系统 │  │     横向滚动，激活态高亮
│  └──────┘ └──────┘ └──────┘ └──────┘  │
├─────────────────────────────────────────┤
│                                         │
│  [根据选中 Tab 动态渲染对应内容面板]      │
│                                         │
└─────────────────────────────────────────┘
```

- **入口**：`switchTab('admin')`。项目**没有 hash 路由**（无 hashchange 监听），页面切换靠 `switchTab(tab)` + `sessionStorage.lastPage` 恢复机制
- **指定默认子 Tab**：沿用项目惯例（参考 `pendingPlanTab` 模式）：`sessionStorage.setItem('pendingAdminTab', 'payments'); switchTab('admin')`，admin.js 加载时读取并清除
- **顶栏返回**：点击 ← 回到个人中心（`switchTab('profile')`）
- **Tab 栏**：4 个 Tab，使用 `overflow-x: auto` 横滚，避免在窄屏换行

### 3.2 路由注册

在 `main-fusion.js` 中（注意：`switchTab` 与 `switchTabLoad` 是**两个函数**，titles 映射、模块加载逻辑各有一份，**两处都要加**）：

1. **`_ensurePage`** 新增（与现有 `admin-payments` 写法一致）：
   ```js
   else if (id === 'admin') el.innerHTML = '<div id="adminContent"></div>';
   ```

2. **`switchTabLoad` / `switchTab` 的模块加载分支** 新增：
   ```js
   if (tab === 'admin') {
     _mod('admin').then(function (m) {
       m.loadAdmin(document.getElementById('adminContent'));
     });
   }
   ```

3. **两份 `titles` 映射** 均新增：
   ```js
   'admin': '管理后台',
   ```

4. **旧入口重定向**（参考 `myplan → plan` 的既有重定向模式）：
   ```js
   if (tab === 'admin-payments' || tab === 'admin-referrals') {
     try { sessionStorage.setItem('pendingAdminTab',
       tab === 'admin-payments' ? 'payments' : 'referrals'); } catch (e) {}
     switchTab('admin');
     return;
   }
   ```

5. **前端权限守卫**：`switchTab` 现仅有登录守卫（`publicTabs` + `hasAuthToken()`），无角色守卫。在 `admin.js` 的 `loadAdmin()` 入口处校验：
   ```js
   var session = getAuthSession();
   var roles = (session && session.roles) || [];
   if (roles.indexOf('super_admin') < 0 && roles.indexOf('ops_admin') < 0) {
     toast('无权限'); switchTab('home'); return;
   }
   ```
   前端守卫仅是体验层，真正的防线是后端 permission 校验（§5.4）。

**数据 API**：

| 操作 | API action | 权限 | 说明 |
|------|-----------|------|------|
| 用户列表 | `user-list` | `user:view` | **全量返回（无分页）**，当前用户量小，前端过滤即可 |
| 创建用户 | `user-create` | `user:create` | 入参 `username` + `roleCode`；**返回 `tempPassword`（临时密码）**，且 `mustChangePassword=true` |
| 启用/禁用 | `user-update-status` | `user:disable` | `userId` + `status`（active/disabled/locked） |
| 解锁账号 | `user-update-status` | `user:disable` | `userId` + `op: 'unlock'` |
| 分配角色 | `user-role-update` | `role:assign` | `userId` + `roleCodes[]` |
| 角色列表 | `role-list` | `role:view` | 角色 + 权限详情 |
| 权限修改 | `role-permission-update` | `role:permission_manage` | `roleCode` + `permissionCodes[]` |

**需后端扩展**：`listUsers()` 当前仅返回 `id / username / status / mustChangePassword / lastLoginAt / passwordUpdatedAt / createdAt`，**不含角色**。列表要显示角色徽标，需在 `auth-service.js` 的 `listUsers()` 中 LEFT JOIN `user_roles`/`roles` 返回 `roles[]` 数组（一次 join 查询，开销可忽略）。

> 旧版文档 mock 中的「订阅状态 / 返利金额 / 登录 IP」字段在 `user-list` 中均不存在，需跨表聚合订阅与返利数据，列为**远期增强**，本期不做。

**交互行为**：

- **搜索**：输入用户名或 ID，200ms 防抖前端过滤
- **筛选**：全部 / 正常（active）/ 禁用（disabled）/ 锁定（locked）
- **编辑角色**：弹出 Bottom Sheet，勾选角色（**super_admin / ops_admin / analyst / viewer 四种**），确认后调用 `user-role-update`
- **查看详情**：弹出面板，展示 `user-list` 实际返回字段：注册时间、最近登录时间、密码更新时间、是否需改密码、角色
- **创建用户**：弹出表单，输入用户名 + 选择角色；**创建成功后必须以醒目弹窗展示 `tempPassword`，并提示「请复制并转交用户，关闭后无法再次查看」**（后端只存哈希，无法找回）
- **角色权限管理**：跳转子面板，展示 4 个角色的权限 checklist（permission code 见 §5.1）；`super_admin` 行只读展示 `*`
- **按钮级权限**：`ops_admin` 进入本 Tab 时只读（有 `user:view`/`role:view`，无写权限），所有操作按钮隐藏

## 5. 权限与入口

### 5.1 角色与权限体系（代码实况）

`auth-service.js` 定义 **4 个内置角色**（不是旧版文档写的 admin/editor/viewer）：

| 角色 | 定位 | 管理后台可见性 |
|------|------|--------------|
| `super_admin` | 超级管理员，权限 `*` 通配 | 全部 4 个 Tab，全部写操作 |
| `ops_admin` | 运维管理员，有 `user:view`/`role:view` + 全部 `ops:*`，**无用户写权限** | 用户 Tab（只读）+ 系统 Tab（可操作）；订阅/返利 Tab 默认不可见 |
| `analyst` | 分析师，业务查看权限 | 无管理后台入口 |
| `viewer` | 普通用户 | 无管理后台入口 |

权限粒度为 permission code（如 `user:create`、`role:assign`、`ops:backfill`），后端通过 `ACTION_PERMISSION_MAP` 将 action 映射到所需 permission，`hasPermission()` 校验（super_admin 直接放行）。

### 5.2 访问控制

| 层级 | 机制 |
|------|------|
| 前端入口可见性 | `getAuthSession().roles` 含 `super_admin` 或 `ops_admin` 时，profile 页渲染「🔧 管理后台」卡片 |
| 前端页面守卫 | `loadAdmin()` 入口校验 roles，无权限 toast + 跳首页（§3.2 第 5 点） |
| 前端按钮级 | 按 `session.permissions` 含对应 code 决定是否渲染写操作按钮 |
| **后端（真正防线）** | action 级 permission 校验；返回 `{code: 403, msg: 'FORBIDDEN', permission}` |

### 5.3 入口设计

**入口 1：个人中心（推荐）**——`profile.js` 当前**尚无任何管理入口**（旧版文档误称已有），需新增：

```
profile.js → getAuthSession().roles 含 super_admin / ops_admin
    → 在操作链接区渲染「🔧 管理后台」入口（与现有 profile-act-link 同栏样式）
    → 点击 switchTab('admin')
```

**入口 2：旧入口重定向**——`switchTab('admin-payments'/'admin-referrals')` 自动转入统一后台对应 Tab（§3.2 第 4 点），不存在 hash 书签问题（项目无 hash 路由）。

### 5.4 🔴 P0：后端权限加固（先于 UI 开发）

在 `server/auth-service.js` 中：

1. `PERMISSIONS` 数组新增：`'payment:admin'`、`'referral:admin'`（连同 §4.4 的 `ops:error_log_view`、`ops:refresh_predictions`）
2. `ACTION_PERMISSION_MAP` 新增 6 行映射：

```js
'admin-subscription-list':        'payment:admin',
'admin-grant-subscription':       'payment:admin',
'admin-referral-commissions':     'referral:admin',
'admin-referral-accounts':        'referral:admin',
'admin-referral-withdraw-list':   'referral:admin',
'admin-referral-withdraw-process':'referral:admin',
```

3. `ROLE_PERMISSION_MATRIX` **不变**——`super_admin` 的 `*` 自动覆盖新 permission，其余角色一律 403。如未来要授权 ops_admin 管订阅，再向矩阵添加即可
4. 需重建/升级权限种子数据（`seedRolesAndPermissions` 是 `INSERT OR IGNORE`，新增 code 会自动补种，确认部署后执行一次初始化）

**验收**：用 viewer 账号调用 `admin-grant-subscription` 必须返回 403。

## 8. 技术实现要点

### 8.1 模块加载与子 Tab 传递

```js
// admin.js — 与其他 pages 模块签名保持一致
import { api } from '../api.js';
import { getAuthSession } from '../auth-client.js';

export async function loadAdmin(container) {
  // 1. 前端权限守卫（§3.2 第 5 点）
  // 2. 读取并清除 pendingAdminTab（项目惯例，参考 pendingPlanTab）
  var tab = 'users';
  try {
    var pending = sessionStorage.getItem('pendingAdminTab');
    if (pending) { tab = pending; sessionStorage.removeItem('pendingAdminTab'); }
  } catch (e) {}
  renderTabBar(container, tab);
  switchTabContent(tab);
}

async function switchTabContent(tab) {
  switch (tab) {
    case 'users':     await renderUsersTab();     break;
    case 'payments':  await renderPaymentsTab();  break;
    case 'referrals': await renderReferralsTab(); break;
    case 'system':    await renderSystemTab();    break;
  }
}
```

### 8.2 移植策略：重写而非 import

旧版文档计划 `import { renderPaymentsTab } from './admin-payments.js'` 复用——**实测不可行**：

1. 两个旧页面的 API 调用全部是失配的旧签名（`api('/api', {action, token: true})`），每一处都要改
2. 全局函数挂 `window.*`（`window.loadAdminSubPage` / `window.grantSubscription` / `window.processWithdraw`），并入容器页会产生命名冲突
3. 两文件合计仅 ~200 行，重写成本低于改造成本

正确调用方式（token 由 api.js 自动注入请求头）：

```js
// ✅ 新签名
const list = await api('admin-subscription-list', { status: 'active', pageSize: 30 });
// ❌ 旧页面的失配写法（'/api' 会被当成 action）
// await api('/api', { action: 'admin-subscription-list', token: true, ... });
```

注意 api.js 的返回约定：`code===1` 时 resolve `d.data`（不是整个响应体）；401 自动清登录态并广播 `auth:unauthorized`；403 会走 reject（`err.code === 403`），UI 层 catch 后提示「无权限」。

### 8.3 CSS 设计原则

- 复用 `app.css` 中的 `:root` 变量（`--bg: #111820`、`--card`、`--text`、`--cyan: #7ea6bd`、`--radius: 16px` 等，均已存在）
- Tab 栏 `display: flex; overflow-x: auto` 支持窄屏横向滚动
- 按钮最小触摸目标 44×44px
- 列表卡片间距 8px，内边距 12px
- 角色标签用圆角 pill（`border-radius: 99px`），4 角色各配一色：super_admin 红、ops_admin 琥珀、analyst 青、viewer 灰
- 操作按钮使用项目统一的 `--cyan` 风格
- **不要复用 payments.css 的 `.admin-*` 类**（白底紫字的旧风格），admin.css 自成体系，类名前缀 `adm-` 避免冲突

### 8.4 移动端适配

- **页面最大宽度**：440px（与主站一致）
- **字体大小**：卡片标题 14px，内容 12px，统计数字 20px
- **点击区域**：行内按钮至少 44px 高度
- **弹窗**：Bottom Sheet 风格（角色选择、用户详情、创建用户、临时密码展示）
- **搜索框**：sticky 定位，滚动时保持在顶部
