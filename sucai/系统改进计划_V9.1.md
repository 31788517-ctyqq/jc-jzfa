## Phase 3：架构优化 🔵 中优先级（下月完成）

### 3.1 API 路由拆分

**现状**：`server/index.js` 7146 行，所有 40+ 个 action 全部在一个 `switch (action)` 语句中。
单一文件包含：认证、用户管理、数据抓取、赔率查询、AI 预测、方案生成、回测、热度计算、功守道分析、WebSocket 等。

**问题**：
- 文件过大，编辑器加载慢，IDE 分析困难
- 多人协作易冲突
- 单元测试难以隔离
- 新增 action 时无明确归属

**拆分方案**（按业务域）：

```
server/
├── index.js          (精简至 ~500 行：Express 初始化 + 中间件 + 路由注册)
├── routes/
│   ├── auth.js       (auth-login, auth-session, auth-logout, auth-change-password)
│   ├── users.js      (user-list, user-create, user-update-status, ...)
│   ├── plans.js      (plan-list, plan-generate, plan-confirm, ...)
│   ├── matches.js    (match-list, match-odds, match-detail, ...)
│   ├── predictions.js (predict, prediction-backtest, prediction-stats, ...)
│   ├── gongshoudao.js (gs-cache, gs-analysis, gs-pk, ...)
│   ├── hot.js        (hot-data, quant-hot, jczq-change, ...)
│   ├── ai.js         (ai-batch-generate, ai-cache, ai-timing, ...)
│   └── system.js     (health, cache-flush, data-sync-trigger, ...)
```

**实施步骤**：
- [ ] 第 1 步：抽取 `auth.js` 路由（最简单，7 个 action，逻辑独立）
- [ ] 第 2 步：抽取 `users.js` 路由
- [ ] 第 3 步：抽取 `plans.js` 路由（最复杂，与 data.json/odds_history 耦合深）
- [ ] 第 4 步：逐步迁移其余模块
- [ ] 全程保持 `POST /api` 接口不变，前端无感知

**风险控制**：
- 每次拆分后运行 `npm run test:critical` + `npm run test:e2e:critical`
- 保留原 `index.js` 作为备份分支 `backup/monolithic-index`

## Phase 4：支付体系与订阅收费 💰 核心业务（本月启动，2 个月交付）

### 4.0 业务背景

当前系统仅有免费注册用户（viewer/editor/admin 角色），无商业化能力。需建立：
- **订阅收费体系**：全功能开放，仅按付费周期区分（月/季/年）
- **自动化续费与过期管理**：到期提醒、自动续费、过期停用
- **支付集成**：支付宝为主支付渠道（H5 手机网站支付 + 电脑网站支付）

> **核心原则**：所有付费用户均可使用系统的**全部功能**，不做功能阉割。
> 套餐差异仅在**付费周期和单价折扣**上，长周期更优惠。

---

### 4.1 套餐设计（月费锚点 ¥98）

| 套餐 | plan_code | 价格 | 折合月费 | 折扣 | 相比月付省 |
|------|-----------|------|---------|------|-----------|
| **月度套餐** | `monthly` | ¥98 | ¥98/月 | 基准价 | — |
| **季度套餐** | `quarterly` | ¥258 | ¥86/月 | ≈88折 | 省 ¥36 |
| **年度套餐** | `yearly` | ¥888 | ¥74/月 | ≈76折 | 省 ¥288 |

**定价逻辑**：
- 月费 ¥98 为锚点，覆盖 AI 预测+数据+方案的日常运营成本
- 季度套餐 ≈12% 折扣，锁定 3 个月用户粘性
- 年度套餐 ≈24% 折扣，最大化用户生命周期价值（LTV）

**对比参考**（竞品价格带）：
- 竞彩猫/懂球帝会员：¥30-68/月
- 500彩票网高级会员：¥88-128/月
- JC-ZJFA 定价 ¥98/月处于**中高端**，依托 AI 双模型 + 功守道独有分析能力


#### 4.4.3 订阅状态守卫中间件

```javascript
// server/payments/subscription-guard.js

/**
 * 订阅状态守卫 — 仅检查是否在有效期内
 * 不做功能分级拦截（全功能开放）
 * @returns {Function} Express 中间件
 */
function requireActiveSubscription(req, res, next) {
  const status = req.authSession?.subscription_status;
  
  // free 用户（从未付费）→ 引导付费
  if (!status || status === 'free') {
    return res.json({ 
      code: 402, 
      msg: 'SUBSCRIPTION_REQUIRED', 
      data: { redirect: 'pricing' }
    });
  }
  
  // 已过期 → 引导续费
  if (status === 'expired') {
    return res.json({ 
      code: 402, 
      msg: 'SUBSCRIPTION_EXPIRED', 
      data: { 
        expiredAt: req.authSession.subscription_expires_at,
        redirect: 'subscription'
      }
    });
  }
  
  next();
}

/**
 * 可选订阅 — 未付费用户也能访问，但返回降级内容
 */
function optionalSubscription(req, res, next) {
  // 不阻断，让业务层根据 req.authSession.subscription_status 决定返回内容
  next();
}
```

**应用到现有 action**：
- `plan-list`：免费用户可看前 3 个，付费用户全量
- `prediction-backtest` / `ai-prediction-detail` / `odds-history`：`requireActiveSubscription`
- `gs-analysis`：`requireActiveSubscription`
- `plan-generate` / `plan-confirm`：`requireActiveSubscription`

**`subscription_status` 如何注入 `authSession`**：

采用「登录时写入 + 定时刷新」策略，避免每个请求都查库：

```javascript
// 方案：在 auth-session 处理中，登录时查询 users 表写入 session
// server/routes/auth.js (或现有 auth 逻辑)
const user = await adp.execOne(
  'SELECT subscription_status, subscription_expires_at FROM users WHERE id = ?',
  [userId]
);
// 写入 session 对象，后续请求直接读取
authSession.subscription_status = user.subscription_status;
authSession.subscription_expires_at = user.subscription_expires_at;

// 注意：如果用户续费/升级，前端重新调用 auth-session 刷新 session 数据
// 过期由 renewal-scheduler 定时更新 users 表，用户下次请求自然读到新状态
```

#### 4.4.4 自动续费与过期处理

> **注意**：支付宝周期扣款需要用户单独签约协议，流程复杂且审核周期长。
> 本方案采用「到期提醒 + 手动续费」策略，降低实现成本。

```javascript
// server/payments/renewal-scheduler.js

// 每天凌晨 2:00 执行 cron 任务：
// 1. 【到期前 3 天提醒】查询 3 天后到期的 active 订阅：
//    a. auto_renew=1 → 发送站内通知 + 推送「您的会员即将到期，点击续费」
//    b. auto_renew=0 → 发送站内通知「您的会员即将到期」
// 2. 【到期当天处理】查询今日到期的订阅：
//    → 状态改为 expiring_soon（进入 3 天宽限期，只读模式）
// 3. 【宽限期过后】expiring_soon 超过 3 天 → 状态改为 expired

// 过期处理事务：
// BEGIN TRANSACTION;
//   UPDATE user_subscriptions SET status='expired'
//     WHERE status='expiring_soon' AND date(end_date, '+3 days') < date('now');
//   UPDATE users SET subscription_status='expired' 
//     WHERE id IN (SELECT user_id FROM user_subscriptions WHERE status='expired');
// COMMIT;
```

### 4.6 支付宝接入要点

#### 4.6.1 支付方式选择

| 场景 | 支付宝产品 | 接口 | 用户体验 |
|------|-----------|------|---------|
| 手机 H5 | **手机网站支付** | `alipay.trade.wap.pay` | 自动唤起支付宝 App，未安装则跳转 H5 收银台 |
| 桌面浏览器 | **电脑网站支付** | `alipay.trade.page.pay` | 跳转支付宝网页收银台，扫码或登录支付 |
| 兜底方案 | **扫码支付** | `alipay.trade.precreate` | 生成二维码，用户支付宝扫码付 |

**推荐策略**：前端自动检测设备 → 手机走 `wap.pay`，桌面走 `page.pay`，统一体验。

#### 4.6.2 为什么支付宝更适合本项目？

| 对比维度 | 微信支付 | 支付宝（✅ 采用） |
|---------|:-------:|:-----:|
| H5 网页支付 | 需要 Native 扫码（体验差） | **手机网站支付**，直接唤起 App 或跳转 H5 收银台 |
| 回调机制 | 需额外配置域名 | 异步通知 + 同步跳转，双保险 |
| 商户审核 | 严格，周期 2-4 周 | 相对宽松，1-2 周 |
| SDK 支持 | 较封闭 | **alipay-sdk npm 包**，Node.js 友好 |
| 退款流程 | 复杂 | `alipay.trade.refund` 简洁 |

#### 4.6.3 接入步骤（8 步闭环）

```
步骤 1: 注册支付宝开放平台 + 创建应用
  ├── 访问 open.alipay.com
  ├── 创建「网页/移动应用」
  ├── 签约「手机网站支付」+「电脑网站支付」产品
  └── 获取 appId + 配置密钥

步骤 2: 密钥配置
  ├── 生成 RSA2 应用私钥（openssl genrsa）
  ├── 上传公钥到支付宝开放平台 → 获取支付宝公钥
  ├── 存储私钥到 server/.env（不提交 git）
  └── 配置 notify_url（异步回调地址）

步骤 3: 安装 SDK
  npm install alipay-sdk --save

步骤 4: 创建支付订单 API
  action: payment-create-order
  ├── 接收 plan_code + period
  ├── 服务端查询价格（不信任前端传值）
  ├── 生成商户订单号（ZJ + 时间戳 + 随机数）
  ├── 调用 alipay-sdk → 获取支付跳转链接
  └── 返回 { paymentUrl, orderNo }

步骤 5: 前端跳转支付
  ├── 移动端: location.href = paymentUrl（唤起支付宝 App）
  ├── 桌面端: window.open(paymentUrl) 或 iframe
  └── 显示「支付中...」状态

步骤 6: 支付回调处理
  ├── 同步跳转: returnUrl → payment-result 页面
  └── 异步通知: notifyUrl → 验证签名 → 更新订单 + 激活订阅

步骤 7: 支付结果页
  ├── 查询订单状态（alipay.trade.query）
  ├── 成功 → 显示套餐详情 + 到期日
  └── 失败 → 重新支付入口

步骤 8: 退款接口
  alipay.trade.refund → 争议处理 / 用户申诉
```

#### 4.6.4 alipay.js 核心封装

```javascript
// server/payments/alipay.js
const AlipaySdk = require('alipay-sdk').default;
const AlipayFormData = require('alipay-sdk/lib/form').default;

const alipaySdk = new AlipaySdk({
  appId: process.env.ALIPAY_APP_ID,
  privateKey: process.env.ALIPAY_PRIVATE_KEY,    // 应用私钥
  alipayPublicKey: process.env.ALIPAY_PUBLIC_KEY, // 支付宝公钥
  gateway: 'https://openapi.alipay.com/gateway.do',
```

#### 4.6.5 安全要点

- 支付回调必须验证支付宝签名（使用支付宝公钥）
- 验证 seller_id（确认是自家商户）和 app_id（确认是自家应用）
- 订单金额必须在服务端校验（不信任前端传值）
- 支付回调幂等处理（同一 trade_no 不重复激活）
- callback action **不使用用户 token 认证**，改用签名校验
- 必须返回 `"success"` 字符串，否则支付宝会重复通知

### 4.10 邀请返利模块完整设计 🔗

#### 4.10.0 业务规则

```
核心规则：
1. 返利基于被邀请人实付金额（优惠码折扣后），按阶梯比例计算
2. 阶梯仅与该被邀请人的付费次数相关，不跨用户累计
3. 同一被邀请人的每次付费都触发一次返利（不限总次数）
4. 免费试用（trial）和手动开通（admin_grant）不触发返利
5. 返利金额 = floor(实付金额 × 阶梯比例)，向下取整到分
6. 退款订单对应的返利自动取消（status → cancelled）
7. 邀请关系绑定时机：通过邀请链接注册时填充 referred_by
8. 返利发放时机：被邀请人支付回调成功后，异步计算并写入
9. 返利结算方式：统一线下结算（不提供线上实时转账）
```

#### 4.10.1 返利阶梯费率

| 付费次数 | 返利比例 | 示例（年度套餐 ¥888） | 示例（季度套餐 ¥258） | 示例（月度套餐 ¥98） |
|:--------:|:--------:|---------------------|---------------------|---------------------|
| **第 1 次** | **50%** | 返 ¥444 | 返 ¥129 | 返 ¥49 |
| **第 2 次** | **55%** | 返 ¥488 | 返 ¥141 | 返 ¥53 |
| **第 3 次** | **60%** | 返 ¥532 | 返 ¥154 | 返 ¥58 |
| **第 4 次及以后** | **60%** | 返 ¥532 | 返 ¥154 | 返 ¥58 |

> **设计意图**：首次付费 50% 高额激励获客，后续递增至 60% 封顶，鼓励同一被邀请人持续续费。

**阶梯判断逻辑**（在 `payment-callback` 成功后触发）：

```javascript
// server/payments/referral-compute.js

/**
 * 计算本次返利比例和金额
 * @param {number} inviteeUserId - 被邀请人 ID
 * @param {number} paidAmount - 实付金额（分）
 * @returns {{ paymentIndex: number, rate: number, commissionAmount: number }}
 */
async function computeCommission(inviteeUserId, paidAmount) {
  // 1. 查询该被邀请人的历史付费次数（不含 trial 和退款订单）
  const paymentCount = await adp.execOne(
    `SELECT COUNT(*) as cnt FROM referral_commissions 
     WHERE invitee_user_id = ? AND status != 'cancelled'`,
    [inviteeUserId]
  );
  
  // 2. 确定本次是第几次付费（1-based）
  const paymentIndex = (paymentCount?.cnt || 0) + 1;
  
  // 3. 阶梯费率映射
  const rateMap = { 1: 50, 2: 55 };  // 第3次及以后 = 60
  const rate = rateMap[paymentIndex] || 60;
  
  // 4. 计算返利金额（分），向下取整
  const commissionAmount = Math.floor(paidAmount * rate / 100);
  
  return { paymentIndex, rate, commissionAmount };
}
```

```javascript
// server/payments/referral-anti-fraud.js

/**
 * 邀请反欺诈检查（在 onPaymentSuccess 中调用）
 * @returns {{ passed: boolean, reason?: string }}
 */
async function antiFraudCheck(inviteeUserId, paymentOrderId) {
  // 1. 检查邀请人与被邀请人是否为同一支付账号
  const order = await adp.execOne(
    `SELECT po.user_id, u.referred_by FROM payment_orders po
     JOIN users u ON u.id = po.user_id WHERE po.id = ?`,
    [paymentOrderId]
  );
  // 自邀请检测（同一设备指纹）
  const sameDevice = await adp.execOne(
    `SELECT COUNT(*) as cnt FROM users 
     WHERE id IN (?, ?) AND device_fingerprint IS NOT NULL
     AND device_fingerprint = (SELECT device_fingerprint FROM users WHERE id = ?)
     AND id != ?`,
    [order.user_id, order.referred_by, order.user_id, order.referred_by]
  );
  if (sameDevice?.cnt > 0) {
    return { passed: false, reason: 'same_device_fingerprint' };
  }
  
  // 2. 检查同一 IP 24h 内注册次数
  // （需要 device_fingerprint 和 registration_ip 字段已在 users 表中）
  
  return { passed: true };
}
```

#### 4.10.5 返利计算引擎（与支付回调集成）

```javascript
// server/payments/referral-compute.js
// 该模块在 alipay-callback.js 支付成功后调用

const adp = require('../core/database').getAdapter();
const { antiFraudCheck } = require('./referral-anti-fraud');

/**
 * 支付成功后检查是否需要计算返利
 * 调用入口：alipay-callback.js 中订单状态变为 paid 后
 */
async function onPaymentSuccess(paymentOrderId) {
  // 1. 查支付订单信息
  const order = await adp.execOne(
    `SELECT po.*, u.referred_by 
     FROM payment_orders po
     JOIN users u ON u.id = po.user_id
     WHERE po.id = ? AND po.pay_status = 'paid'`,
    [paymentOrderId]
  );
  if (!order) return { triggered: false, reason: 'order_not_found' };
  if (!order.referred_by) return { triggered: false, reason: 'not_invited' };
  if (order.plan_code === 'trial' || order.pay_channel === 'manual') {
    return { triggered: false, reason: 'non_commissionable' };
  }

  // 2. 反欺诈检查
  const fraudCheck = await antiFraudCheck(order.user_id, paymentOrderId);
  if (!fraudCheck.passed) return { triggered: false, reason: fraudCheck.reason };

  // 3. 幂等检查：此订单是否已计算过返利
  const existing = await adp.execOne(
    `SELECT id FROM referral_commissions WHERE payment_order_id = ?`,
    [paymentOrderId]
  );
  if (existing) return { triggered: false, reason: 'already_computed' };

  // 4. 计算返利比例
  const { paymentIndex, rate, commissionAmount } = await computeCommission(
    order.user_id,  // invitee
    order.amount
  );

  // 5. 写入返利记录
  const subscription = await adp.execOne(
    `SELECT id FROM user_subscriptions WHERE transaction_id = ? ORDER BY id DESC LIMIT 1`,
    [order.transaction_id]
  );

  await adp.execRun(
    `INSERT INTO referral_commissions 
     (inviter_user_id, invitee_user_id, payment_order_id, subscription_id,
      payment_index, commission_rate, payment_amount, commission_amount, status)
     VALUES (?, ?, ?, ?, ?, ?, ?, ?, 'pending')`,
    [order.referred_by, order.user_id, paymentOrderId, 
     subscription?.id || null, paymentIndex, rate, order.amount, commissionAmount]
  );

  // 6. 更新邀请人账户
  const isFirstCommission = await adp.execOne(
    `SELECT COUNT(*) as cnt FROM referral_commissions 
     WHERE inviter_user_id = ? AND invitee_user_id = ? AND status != 'cancelled'`,
    [order.referred_by, order.user_id]
  );
  const isNewInvitee = (isFirstCommission?.cnt || 0) <= 1;

  await adp.execRun(
    `INSERT INTO referral_accounts (user_id, total_earned, total_invitees, total_commissions)
     VALUES (?, ?, ?, 1)
     ON CONFLICT(user_id) DO UPDATE SET
       total_earned = total_earned + ?,
       total_commissions = total_commissions + 1,
       total_invitees = total_invitees + ?,
       updated_at = datetime('now','localtime')`,
    [order.referred_by, commissionAmount, isNewInvitee ? 1 : 0, commissionAmount, isNewInvitee ? 1 : 0]
  );

  return {
    triggered: true,
    paymentIndex,
    rate,
    commissionAmount,
    inviterId: order.referred_by,
    inviteeId: order.user_id
  };
}

/**
 * 退款时取消对应返利
 */
async function onPaymentRefunded(paymentOrderId) {
  await adp.execRun(
    `UPDATE referral_commissions SET status = 'cancelled', remark = '订单已退款'
     WHERE payment_order_id = ? AND status = 'pending'`,
    [paymentOrderId]
  );
  // 注意：不自动回退账户余额，由管理员在提现审核时手动处理
}

module.exports = { onPaymentSuccess, onPaymentRefunded, computeCommission };
```

#### 4.10.6 账户机制

```
账户生命周期：
  ┌──────────────────────────────────────────────────┐
  │ 用户首次成功邀请他人付费                           │
  │ → 自动创建 referral_accounts 记录                 │
  │ → total_earned 累加                               │
  │ → balance = total_earned - total_withdrawn        │
  │                                                   │
  │ 每次新的返利触发                                   │
  │ → total_earned += commission_amount               │
  │ → total_commissions += 1                          │
  │ → 首次邀请该用户 → total_invitees += 1            │
  │                                                   │
  │ 提现                                              │
  │ → 发起 withdrawal 请求                            │
  │ → 管理员线下打款                                   │
  │ → 标记 completed                                  │
  │ → total_withdrawn += withdrawal_amount            │
  └──────────────────────────────────────────────────┘

账户查询 API 返回结构：
{
  code: 0,
  data: {
    totalEarned: 58590,         // 累计收入（分）= ¥585.90
    totalWithdrawn: 0,          // 已提现
    balance: 58590,             // 可用余额（分）
    totalInvitees: 1,           // 成功邀请人数
    totalCommissions: 2,        // 返利笔数
    pendingCommissions: 58590,  // 待结算返利（status=pending 的总和）
    recentCommissions: [...]    // 最近 10 条返利记录
  }
}
```

#### 4.10.7 线下提现流程

```
提现流程：
  ① 用户在「返利账户」页查看可用余额
  ② 点击「申请提现」→ 填写提现金额 + 收款方式 + 收款账号
  ③ 系统校验：
     - 提现金额 ≤ balance
     - 最小提现额 ¥10（1000 分）
     - 收款信息完整性
  ④ 写入 referral_withdrawals 表（status=submitted）
  ⑤ 管理员后台看到待处理提现
  ⑥ 管理员线下打款（银行转账/微信/支付宝）
  ⑦ 打款完成后在后台标记「已完成」
     → referral_withdrawals.status = 'completed'
     → referral_accounts.total_withdrawn += 提现金额
  ⑧ 用户端看到提现状态变为「已到账」

管理员后台操作：
  - 提现列表：按状态筛选（submitted/processing/completed/rejected）
  - 审核操作：改为 processing → 线下打款 → 改为 completed
  - 驳回操作：改为 rejected + 填写驳回原因（站内通知用户）
  - 导出报表：按时间段导出返利+提现汇总

防重复机制：
  - 同一 withdrawal 已 completed 后不可再次操作
  - 提现提交时不做余额冻结（初期不做，量上来后完善）
```

## Phase 5: 技术升级 🟢 低优先级（季度内评估）

### 5.1 TypeScript 渐进引入

**适用场景**：随着项目规模增长（596 个 JS 文件），类型安全变得越来越重要。

**方案**：渐进式引入，不影响现有 JS 代码运行。

```
第 1 步：添加 tsconfig.json + TypeScript 编译配置（allowJs: true）
第 2 步：给 server/config.js → server/config.ts（纯类型定义，收益最大）
第 3 步：给 server/routes/ 目录下的新模块用 .ts 编写
第 4 步：给 server/core/ 核心模块逐步迁移
```

**不做的**：

### 5.2 H5 前端架构评估

**现状**：`preview/` 下 17 个页面模块，纯 Vanilla JS，无组件化框架。

**评估要点**：
- 如果未来 3 个月内不打算新增超过 3 个页面 → **保持现状**（当前架构够用）
- 如果计划大幅扩展 H5 功能 → 考虑引入轻量框架

**如果决定引入框架**：
- **推荐方案**：Alpine.js（极轻量，5KB，兼容现有 Vanilla JS）
- **备选方案**：Preact（React 替代，3KB，但需要构建工具）
- **不推荐**：Vue/React 全套（迁移成本极高，破坏现有架构）

**行动项**：

### 5.3 前后端分离评估

**现状**：Express 既提供 API 也 serve 静态文件（preview/）。这种模式在中小型项目中完全合理。

**评估结论**：**暂时不需要分离**。理由：
1. 当前无独立前端团队
2. 静态文件 SPA 模式部署简单
3. Nginx 已经承担了静态文件服务（生产环境），Express 只做开发代理

**如果未来需要分离**：将 `preview/` 移到独立仓库，用 Vite 构建，部署到 CDN。
