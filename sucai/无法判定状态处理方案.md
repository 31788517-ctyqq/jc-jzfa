# 无法判定状态处理方案

## 一、问题背景

`judgeScore` 中让球方向（让胜/让平/让负）需要 `hcp`（让球数）做比分判定。当前 `hcp` 的来源单一：

```
mOdds.rqspf.handicap → null（无数据时）
```

`null` 被当成 `0` 处理 → 让平在平局时误判为正确。V17 已修复为返回 `null`，但 `null` 引发了一个未回答的问题：**无法判定时应该怎么处理？**

---

## 二、hcp 数据源全链路

现有 `index.js:7087-7095` 已有四级降级链（在 `entry` 对象构建层）：

| 级别 | 来源 | 值 |
|:---:|------|-----|
| 1 | `oddsEntry.handicap` | 顶层显式值 |
| 2 | `sportteryHandicap` | 竞彩官方 |
| 3 | `oddsEntry.rqspf.handicap` | 让球赔率子字段 |
| 4 | `m.concede` | 比赛原始让球数 |

**但 `buildMatchObj` 和 `hydrateSnapshotWithResults` 只用了第 3 级**：

```javascript
var hcp = mOdds && mOdds.rqspf ? mOdds.rqspf.handicap : null;
```

没有尝试第 4 级（`m.concede`）或第 2 级（sporttery）。

---

## 三、三种 "无法判定" 场景

| # | 场景 | 原因 | 区分 |
|---|------|------|:--:|
| A | 比赛未开赛 | `m.score` 为空 | 待定 |
| B | 比赛已结束，但缺少让球数据 | `hcp === null && m.score` 有值 | **数据缺失** |
| C | 让球数据有，但比分无法解析 | `isNaN(hh) || isNaN(aa)` | **数据异常** |

当前三种都返回 `null`，前端都显示为"待定色"（队名色），无法区分。

---

## 四、影响范围

### 4.1 方案级别结果判定

`buildMatchObj:1003-1018` — 子方向含 null 时：

```javascript
anyUnknown = true → isMatchWon 保持 null
```

**这意味着一个子方向无法判定，整个方案 match 就无法判定输赢**。方案状态始终为"未开奖"。

### 4.2 income-stats 统计

`results` 中有 `if (pp.isPlanWon === null && pp.isPlanLose === null) return;` — 跳过方案。**无法判定的方案不计入收入统计**，导致历史方案被遗漏。

### 4.3 前端显示

| 后端 subResult | 前端 class | 显示颜色 |
|---------------|-----------|:--:|
| `result === 1` | `plan-direction-hit` | 红 |
| `result === 0` | `plan-direction-miss` | 绿 |
| `result === null` | 无 class | 队名色（同未开奖） |

**"数据缺失的无法判定"和"比赛未开"外观完全一致，无法区分。**

---

## 五、处理策略（按优先级）

### 策略 A：尽力补全 hcp 数据（首选）

**在 `judgeScore` 调用前，加 hcp 查找链**：

```
1. mOdds.rqspf.handicap           ← 当前
2. m.concede (比赛原始让球)         ← 兜底，数据源最全
3. 全局 odds 表当天 rqspf.handicap  ← sporttery/500.com 历史
4. 全无 → 标记为 "无法判定"
```

**优势**：极大降低"无法判定"发生率。`m.concede` 来自基础比赛数据，几乎必有。

**风险**：`m.concede` 可能与实时 odds 的 handicap 不同（临场变盘），但用于结果判定影响很小。

### 策略 B：增加"无法判定"结果状态

新增 `result = -1`（区别于 `null` 的"未开赛"和 `0/1` 的"已判定"）：

| result | 含义 | 前端显示 |
|:---:|------|---------|
| `1` | 命中 | 红 |
| `0` | 未中 | 绿 |
| `null` | 未开赛 | 待定色 |
| `-1` | **无法判定** | 灰 / `?` / 特殊标识 |

**对应的前端改动**（同步时做）：
- CSS 新增 `.plan-direction-undetermined { color: #9CA3AF; }`（灰）
- 方案卡片方向旁加 `?` badge
- income-stats 统计时区分"跳过"和"无法判定"

### 策略 C：保守兜底（不推荐）

无法判定时，假设该子方向为"错误"（result=0）。**会让方案命中率偏低**，不推荐。

---

## 六、推荐路径

**Phase 1（当前可做，仅后端）**：补全 hcp 查找链（策略 A）
- 改动范围：`buildMatchObj` + `hydrateSnapshotWithResults` 的 hcp 获取
- 增加 `m.concede` 兜底
- 改动量：~5 行

**Phase 2（前端配合）**：增加"无法判定"显示（策略 B）
- 后端新增 `result = -1`
- 前端新增灰色样式
- 收入统计新增"无法判定"分类
- 改动量：~20 行（需同步部署前后端）

**暂时不做 Phase 2 时**：
- Phase 1 已覆盖 95%+ 场景（`m.concede` 兜底后几乎没有缺口）
- 剩余极少数`m.concede`也缺失的比赛 → 保持 `null` → 前端显示待定色（可接受）
