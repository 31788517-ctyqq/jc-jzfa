## 1. 数据利用率总体审计

### 1.1 采集→存储→消费 全链路

```
数据采集 (3源 × 40+字段)
  ├─ 500.com (shuju_data) → ✅ 功守道 attack.js + AI Prompt
```

## 3. PK 评分器算法审视

### 3.1 现有 7 维评分体系

```
power(35%) + goal(10%) + heat(10%) + health(10%) + stability(10%) + verify(15%) + winPan(10%) = 100%
```

### 3.2 候选新增维度

| 候选维度 | 数据源 | 计分方法 | 建议权重来源 |
|---------|--------|---------|------------|
| **d8: 欧指概率漂移** | `basic.lastWinRate - basic.winRate` | 漂移 > 0.05 → +分, <-0.05 → -分 | 从 power/verify 各抽 2% |
| **d9: 离散度变化** | `discreteWarning().flagLevel` | warning → ×0.8 罚因子, caution → ×0.9 | 乘法调节器(不占权重) |
| **d10: 盘口一致性** | `basic.lastPan - basic.initPan` vs pwScore 方向 | 一致→bonus, 背离→penalty | 融入 verify 维度 |

### 3.3 权重微调建议

```js
// 当前所有玩法 fix 10% winPan
spf:       { ..., winPan: 0.12 }  // SPF 更需要赢盘率
overUnder: { ..., winPan: 0.05 }  // 大小球与赢盘率弱相关
handicap:  { ..., winPan: 0.15 }  // 让球对赢盘率最敏感
```

### 3.4 verify 维度增强

在当前 7 种矛盾检测上增加 2 种:
- 离散度扩大 + pwScore > 0.15 → penalty 10
- 盘口位移与 pwScore 方向相同 → bonus 5

## 4. AI 预测模块审视

### 4.1 当前 Prompt 注入 vs 可用数据

| 数据源 | 注入状态 | 说明 |
|--------|---------|------|
| 500.com shuju_data | ✅ 已注入 | 攻防全景表 + 近 6 场 WDL |
| JczqBasic 40+ 字段 | ❌ 缺失 | 基本面/欧指/离散度/亚指/大小球/北单 SP |
| 功守道缓存 | ❌ 缺失 | xG/共识/稳定性/比分 TOP3/实力阶梯 |
| JczqChange 热度/支持率 | ❌ 缺失 | 市场资金分布 |
| 北单 SP 隐含概率 | ❌ 缺失 | 市场真实定价 |
| odds_history 赔率变化 | ❌ 缺失 | 赔率时序 |

**核心问题**: AI 做"市场面"分析时全靠模型自身知识库编造，而非系统已有的真实赔率数据。

### 4.2 建议注入结构

```
【系统预计算数据 — 基于此数据进行分析】

一、基本面（JczqBasic 竞彩官方）
- 战力指数: 主{homePower}/100，客{guestPower}/100
- 积分均值: 主场均{homeJiFenHomeAll}分，客场均{awayJiFenGuest}分
- 赢盘率: 主{homeWinPan/2*100}%，客{guestWinPan/2*100}%
- 进攻效率: 主{homeEnterEff}，客{guestEnterEff}
- 防守效率: 主{homePreventEff}，客{guestPreventEff}
- 历史交锋: {jiaoFenDesc}

二、功守道量化分析
- 实力阶梯: {ladderLabel}（{totalAdvantage}）
- 预期进球: 主{xgHome} - {xgAway}客
- 融合共识: {fusionConsensusType}（strong/weak/meltdown）
- 进球分布稳定性: {stabilityOverall}/100
- 比分概率 TOP3: {scores[0..2]}

三、市场面（竞彩 JczqBasic + JczqChange 真实数据）
- 欧指隐含概率: 初{winRate}%/{drawRate}%/{loseRate}% → 临{lastWinRate}%/{lastDrawRate}%/{lastLoseRate}%
- 离散度变化: 初{initDiscreteDiff} → 临{lastDiscreteDiff}（{扩大/收窄}）
- 亚指盘口: 初{initPan} → 临{lastPan}（{升盘/降盘/不变}）
- 大小球盘口: {dxqLastPan}球（初盘{dxqInitPan}）
- 市场支持率: 主{winPercent}% / 平{drawPercent}% / 客{losePercent}%
- 北单 SP 隐含概率: 主{homeImplied}% / 平{drawImplied}% / 客{awayImplied}%
- 市场热度: {hotFocusNum}人关注

四、500.com 战绩（保留原有）
{shujuText}

请在"市场面"和"预测建议"部分优先使用上述真实数据，不要使用模型内部知识编造赔率和盘口信息。
```

### 4.3 AI 适配器解析改进

**现状**: `_parseDirection()` 用关键词匹配解析 AI 文本输出，但 AI 实际输出是 JSON 格式。

**改进**: 先尝试 `JSON.parse(content)` 提取结构化字段，失败才降级为关键词匹配。DeepSeekAdapter 和 DoubaoAdapter 共享同一个解析函数。

## 5. 蓝图模块算法审视

### 5.1 架构总览

```
prediction-fusion.js (§6.4 融合引擎)
 ├─ GongshoudaoAdapter     → ❌ 读取不存在的字段
 ├─ PKScorerAdapter         → ⚠️ 薄封装，依赖外部数据
 ├─ DeepseekAdapter        → ⚠️ 脆弱的关键词解析
 ├─ DoubaoAdapter          → ⚠️ 同上，且与 DeepSeek 不共享逻辑
 ├─ ExpertConsensusAdapter → ✅ 正常
 └─ MarketSignalAdapter    → ⚠️ 仅用基础赔率，忽略所有 JczqBasic

outcome-backfill.js (§6.5 回填) → 方向/大小球/比分 → prediction_outcomes
model-weights.js (功守道内部权重) → 与 prediction-fusion 权重两套独立系统
```

### 5.2 P0 结构性断裂

#### 5.2.1 GongshoudaoAdapter 读取不存在的字段

| 当前读取（不存在） | 应改为（实际存在） | 转换逻辑 |
|------------------|-----------------|---------|
| `gsResult.directionAdvantage.direction` | `cross.spf` + `totalAdvantageRaw` | 取 SPF 概率最高方向 |
| `gsResult.directionAdvantage.confidence` | SPF 最高概率 × 100 | `Math.max(spfWin, spfDraw, spfLose) * 100` |
| `gsResult.goalLine` | `totalGoalsExpect` | 直接映射 |
| `gsResult.predictedScore` | `scores[0].score` | 直接映射 |

**后果**: 功守道适配器始终返回 `null`，从未参与过 6 模型融合投票。

#### 5.2.2 两套独立权重系统

```
System A: model-weights.js          System B: outcome-backfill
  ├─ 功守道内部 3 模型 (A/B/C)        ├─ 蓝图 6 模型 (6 adapters)
  ├─ 数据源: prediction_log            ├─ 数据源: prediction_outcomes
  ├─ 缓存 TTL: 10min                   ├─ 无缓存
  ├─ Softmax T=0.5                     ├─ Softmax T=0.5
  └─ 只在 goal.js fusion.fuse() 用      └─ 只在 prediction-fusion 用
```

**问题**: 权重不共享、回填目标不同、模型命名不一致。

#### 5.2.3 model-weights.js 使用错误的代理指标

- ModelA 权重用 `gs_top_score` 代理 → 这是融合后的众数比分，不是 ModelA 独立预测
- ModelB 权重用 `pk_direction` 代理 → 应直接用功守道 SPF 预测
- ModelC 权重用 `pk_ou_hit` 代理 → 应直接用功守道大小球预测

**改进**: 改为从 `unified_predictions` 表读取实际预测与赛果。

### 5.3 P1 适配器增强

#### 5.3.1 MarketSignalAdapter 升级

**现状**: 仅用 `odds.spf` 基础赔率比较。

**改进**: 集成 data-fusion 多维市场信号:
```js
const { loadBasic, spImpliedProb, discreteWarning, asiaWaterChange } = require('./data-fusion');
const basic = loadBasic(matchInfo.date, matchInfo.num);
if (basic) {
  const spProb = spImpliedProb(basic);
  const discrete = discreteWarning(null, basic);
  const asiaWater = asiaWaterChange(basic);
  direction = weightedDecision(spProb, asiaWater, discrete);
}
```

#### 5.3.2 缺少 3 个高价值适配器

| 适配器 | 数据源 | 预测维度 | 价值 |
|--------|--------|---------|------|
| **JczqBasicAdapter** | jczq_basic_cache | 基本面驱动方向 | 利用 18 个闲置字段 |
| **DataFusionAdapter** | data-fusion.fullFusion() | 7 维融合结果 | 一行调用获全维度预测 |
| **HeatProfileAdapter** | league-heat-profile + jczq_change | 联赛自适应冷门检测 | 补足市场热度维度 |

### 5.4 P2 融合算法微调

| 函数 | 问题 | 改进 |
|------|------|------|
| `_assessConsensus` | 纯票数判定，忽略置信度 | 加权一致性: `weightedAgree = sum(conf_i × match_i) / sum(conf_i)` |
| `_fuseDimension` | 不利用 directionConfidence | 改为 `w × confidence` 而非纯 `w` |
| `_judgeOutcome` | 无让球场景判定 | 增加 handicapHit 维度 |

### 7.2 关键风险控制点

1. **Z-01 部署后必须监控**: 功守道适配器首次返回有效数据后，6 模型共识判定会发生改变——部分比赛可能从 meltdown 变为 weak，属于**预期行为**而非回归。

2. **J-01 需要 A/B 验证**: 部署前后对同一场比赛分别生成 AI 分析，确认"有数据注入"版本的分析更准确、更少编造。

3. **Phase 2 的 5 项可安全并行**: 改动的是功守道不同阶段 (goal/fusion/diff/score/market/pk)，互不依赖。

4. **所有改动均有降级保护**: 当 JczqBasic 缓存不可用时（回填未完成的历史日期），所有新增逻辑自动降级到现有行为。
