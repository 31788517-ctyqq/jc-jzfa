# 首次加载优化方案

> 2026-06-16 | 仅方案，不写代码

---

## 问题定位

### 首页（最多推荐 + 最热场次）、排行页、方案页首次加载慢

**共性根因**：服务端接到第一个请求时才开始计算，I/O + CPU 串行执行。

### 三个页面的冷启动路径

| 页面 | API | 服务端操作 | 瓶颈 |
|------|-----|-----------|------|
| 首页 | `home-bundle` | 读 data.json + odds_history + allplays + GS cache + PK decision map | I/O 密集 + CPU 密集 |
| 排行 | `ranking-list` | 遍历全量比赛 + 专家推荐聚合 + 按方向排序 | CPU 遍历大量数据 |
| 方案 | `plan-list` | 读 data.json + plan-cache + 方案生成 | 缓存命中率低(10min TTL) |

### 已有优化（已生效）

```
✅ home-bundle 批处理（3 合 1）
✅ home-bundle 1 分钟内存缓存
✅ ranking-list 2 分钟内存缓存
✅ plan-list 10 分钟内存缓存
✅ 前端 SWR/sessionStorage 缓存
✅ skeleton 骨架屏
✅ cache-warmer 预热 data.json
```

### 缺失部分

```
❌ 首次请求 = 冷启动 = 所有计算从头来
❌ home-bundle 把 I/O 和 CPU 全塞在一个请求里
❌ 没有定时预热（scheduler 未触发 API 层缓存预热）
❌ 排名和方案页的缓存 TTL 短（2min/10min）
❌ 客户端 waterfall：等待 bundle 完成才开始渲染子模块
```

## 优化方案（按投入产出比排序）

### 策略 A：服务端定时预热（低风险，高收益）🔴 最高优先

**原理**：在用户访问之前，由 `scheduler_v2` 定时触发 API 调用，把结果缓存起来。

```
scheduler_v2 新增定时任务:
  10:00 → 预热 home-bundle?date=今天
  10:05 → 预热 ranking-list?date=今天
  10:10 → 预热 plan-list?date=今天
  14:00 → 再预热一次（下午数据更新）
  16:00 → 再预热一次（方案生成完成）
```

**实现方式**：
- 在 `scheduler_v2.js` 新增一个 `warmApiCache` 任务
- 内部直接调用 handler 函数（不走 HTTP），结果写入内存缓存
- 每次比赛天新增约 3 次函数调用，零网络开销

**效果**：首次用户访问时，缓存已热 → 响应时间从 ~5s → ~50ms（内存命中）

**风险**：🟢 低 — 不改变现有逻辑，只是提前执行

**已有基础**：cache-warmer 已经预热 `data.json` 文件缓存，只需扩展到 API 层

### 策略 B：home-bundle 拆分子模块（中风险，高收益）🟡

**原理**：home-bundle 当前是单请求返回所有数据，一个慢全慢。改为返回 3 个子模块的缓存状态，客户端并行拉取。

```
当前：
  浏览器 → home-bundle → 服务器串行处理 3 个模块 → 返回全部数据

优化：
  浏览器 → home-bundle?mode=light → 服务器返回 match-list（最优先）
  浏览器 → 同时发 3 个并行请求（match-list + ranking-light + home-reconcile）
  服务端每个子模块独立缓存，互不阻塞
```

**前端改动**：
- `home-bundle` 响应拆分为 `{matchList, rankingLight, reconcileData}`
- 客户端先渲染 match-list → 再渲染 ranking → 最后渲染 home-reconcile
- 每个子模块独立 loading 骨架屏

**风险**：🟡 中 — 前端渲染逻辑改动，需逐个模块验证

### 策略 C：增大缓存 TTL + 主动失效（低风险，中收益）🟢

**原理**：当前缓存 TTL 太保守，改为更长 + 精确失效。

| 缓存 | 当前 TTL | 建议 TTL | 失效条件 |
|------|---------|---------|---------|
| home-bundle | 1 分钟 | 10 分钟 | data.json 更新 / GS 缓存刷新 |
| ranking-list | 2 分钟 | 10 分钟 | 专家推荐数变化 |
| plan-list | 10 分钟 | 30 分钟 | 方案快照变更 |

**实现**：在 `data_sync.js` 写入新数据后，主动清除对应缓存键

**风险**：🟢 低 — 只改数字 + 增加缓存清除逻辑

### 策略 D：减少首次数据量（低风险，中收益）🟢

**原理**：home-bundle 返回全量比赛数据（含 PK 决策矩阵），首次加载只需要前 5-8 场比赛。

```
home-bundle 增加参数 ?limit=8：
  只处理前 8 场比赛的 PK 决策和排名
  剩下的在后台异步计算
  客户端下拉时 incremental 加载
```

**风险**：🟢 低 — 新增参数，不影响现有逻辑

## 执行建议

| 优先级 | 策略 | 收益 | 风险 | 工时 |
|:---:|------|------|:---:|:---:|
| 🔴 P0 | A: 服务端定时预热 | 冷启动 5s→50ms | 🟢 | 0.5天 |
| 🟡 P1 | C: 增大缓存 TTL | 重复访问更快 | 🟢 | 0.5天 |
| 🟡 P1 | D: 减少首次数据量 | 首屏渲染提速 | 🟢 | 1天 |
| 🟢 P2 | B: home-bundle 拆子模块 | 渐进式渲染 | 🟡 | 2天 |

**推荐路径**：先做 A+C（1天，立竿见影），再做 D（渐进优化），最后 B（需要充分测试）。
