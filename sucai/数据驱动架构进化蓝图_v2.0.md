## 1. 现状总览

### 1.1 当前数据流

```
外部数据源                      存储                         预测模型              用户
┌──────────┐    ┌──────────────────────┐    ┌──────────────────┐    ┌────────┐
│米斗专家推荐│───▶│ 150+ odds_history JSON│◀───│  功守道 7段管道   │───▶│功守道弹窗│
│500.com赔率│───▶│ 70+ shuju_data JSON  │    │  PK 评分器        │───▶│ PK页面  │
│DeepSeek  │───▶│ midou_data.db(SQLite)│    │  DeepSeek + 豆包  │───▶│ AI看板  │
│豆包      │───▶│ trends.json          │    │  AI 合并器        │───▶│ 专家趋势 │
│          │    │ cache.json            │    │  方案生成器        │───▶│ 今日方案 │
└──────────┘    └──────────────────────┘    └──────────────────┘    └────────┘
```

### 1.2 核心痛点

| 问题 | 影响 |
|------|------|
| JSON 碎片化（250+ 独立文件） | 查询效率低，无法跨日期分析 |
| 预测模型各自为政 | 用户需分别查看，无法交叉验证 |
| 数据源仅 3 个 | 预测维度有限，缺少积分榜/交锋，天气/伤停待试验 |
| 无统一特征工程 | 模型间特征不一致，无法复用 |
| 命中率追踪分散 | 无法系统性评估"哪个模型更准" |
| 新模型接入成本高 | 需要修改前后端多处代码 |

### 3.2 成本审计：现有系统付费依赖

| 模块 | 服务 | 月费估算 | 是否可替代 | 说明 |
|------|------|:--:|:--:|------|
| `server/deepseek.js` | DeepSeek API (v4-pro) | ~¥50-200/月 | 🟡 部分可替代 | AI 五维分析核心引擎，不可丢弃；但可降级模型或减少频次 |
| `server/doubao.js` | 豆包 Seed 2.0 (火山引擎) | ~¥30-100/月 | 🟡 部分可替代 | 与 DeepSeek 交叉验证用；可降级或合并调用 |
| `server/fetch_500odds.js` | 500.com 赔率抓取 | 🟢 免费 | - | 纯 HTML 抓取，反爬加固 |
| `scripts/fetch_league_standings.py` | 500.com 积分榜抓取 | 🟢 免费 | - | 纯 HTML 抓取 |
| `scripts/fetch_500_fenxi*.py` | 500.com 战绩数据 | 🟢 免费 | - | Selenium + requests 抓取 |
| 米斗推荐 | 米斗移动端 API | 🟢 免费 | - | 用账号密码登录，无 API 费用 |

> **关键结论**：蓝图新增数据源（积分榜/交锋/战绩）全部走 500.com 免费抓取，**不引入新付费依赖**。DeepSeek + 豆包是现有系统已承担的 AI 成本，蓝图仅通过 Adapter 模式封装——不增加调用频次、不引入额外费用。天气走 OpenWeatherMap Free 套餐白嫖试用（每日几十次调用完全在免费额度内），伤停优先尝试 500.com 伤停简表免费抓取，效果不佳即弃。XGBoost 零成本（本地 CPU 训练即可），待 feature_store 建好后作为第三阶段自然延伸。

### 3.3 零成本数据源优先路线

```
立刻可做（全部免费）:
  ├── 积分榜入库         → fetch_league_standings.py 已有，接入 league_standings 表
  ├── 交锋记录抓取       → 新建 fetch_h2h.js，抓取 odds.500.com 历史对阵页
  └── 战绩数据细化       → 增强 shuju_data 解析，写入 feature_store

试验性接入（免费试用，效果不佳即弃）:
  ├── 🌤️ 天气数据        → OpenWeatherMap **Free 套餐**，每日几十次调用完全在免费额度内
  │                         先在 feature_store 加 weather 字段试效果，命中率无提升直接不维护
  ├── 🏥 伤停/阵容       → 最有价值的待接入数据（核心缺阵直接改变比赛走向）
  │                         先尝试抓 500.com 伤停简表（部分比赛有），免费可行即接入
  └── 新 AI 模型         → 不引入新的付费 LLM，仅封装现有 DeepSeek + 豆包

AI 降本策略（如需要进一步压缩成本）:
  ├── 减少 AI 调用频次   → 从每 1h 降为每 3h，仅赛前 6h 内高频
  ├── 模型降级           → DeepSeek v4-pro → v3（更便宜）；豆包 Seed 2.0 → Lite
  └── 缓存复用           → AI 分析结果缓存 24h，避免同场比赛重复调用
```

```javascript
// server/core/feature-engine.js — 新增
class FeatureEngine {
  async computeFeatures(matchInfo, context = {}) {
    const features = {};
    const db = database.getAdapter();
    
    // 批量查询避免 N+1
    Object.assign(features, await this._getRecentForm(matchInfo, db));
    Object.assign(features, await this._getH2HFeatures(matchInfo, db));
    Object.assign(features, await this._getStandingsFeatures(matchInfo, db));
    Object.assign(features, await this._getOddsFeatures(matchInfo, context));
    
    await this._saveFeatures(matchInfo, features, db);
    return features;
  }
}
```

### 6.1 统一预测记录

```sql
CREATE TABLE IF NOT EXISTS unified_predictions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  -- 比赛标识

  direction TEXT,                 -- 'home'/'draw'/'away'
  direction_confidence REAL,      -- 0-1
```

### 6.4 预测融合引擎

```javascript
// server/core/prediction-fusion.js — 新增

class PredictionFusionEngine {
  constructor() {
    this.adapters = new Map(); // modelName → Adapter
  }

  /** 注册新模型（一行接入） */
  register(adapter) {
    this.adapters.set(adapter.modelName, adapter);
  }

  /**
   * 融合所有模型的预测
   * 
   * 流程:
   *   1. 并行调用所有适配器 → 收集预测
   *   2. 加载动态权重 (基于各模型近期命中率)
   *   3. 维度级加权合成 → 融合结论
   *   4. 一致性判定 → strong/weak/meltdown
   *   5. 存入 unified_predictions 表
   */
  async fuseForMatch(matchInfo, context) {
    // 并行收集
    const predictions = [];
    const tasks = [...this.adapters.values()].map(async (adapter) => {
      try {
        const pred = await adapter.predict(matchInfo, context);
        if (pred) predictions.push(pred);
      } catch (e) { /* log & skip */ }
    });
    await Promise.all(tasks);

    // 加权合成
    const weights = await this._loadWeights();
    const fusion = this._fuseDimension(predictions, weights);
    const consensus = this._assessConsensus(predictions);

    // 持久化
    await this._saveAll(predictions, fusion, matchInfo);

    return { matchInfo, modelPredictions: predictions, fusion, consensus };
  }
}

// 全局单例，启动时注册
const fusionEngine = new PredictionFusionEngine();
fusionEngine.register(new GongshoudaoAdapter());
fusionEngine.register(new DeepseekAdapter());
// ... 更多模型一行注册
```

```javascript
class GongshoudaoAdapter extends PredictionModelAdapter {
  modelName = 'gongshoudao';
  modelVersion = 'v7.0';
  dimensions = ['direction', 'goal', 'score'];

  async predict(matchInfo, context) {
    // 薄封装：调用现有 computeSingleMatch
    const gs = require('../gongshoudao/index.js');
    const result = gs.computeSingleMatch(context.rawStats, matchInfo);
    if (!result) return null;

    return {
      modelName: this.modelName,
      modelVersion: this.modelVersion,
      direction: result.totalAdvantageRaw > 0.05 ? 'home' : 
                  result.totalAdvantageRaw < -0.05 ? 'away' : 'draw',
      directionConfidence: Math.min(Math.abs(result.totalAdvantageRaw) * 2, 1),
      goalTotal: result.totalGoalsExpect ? parseFloat(result.totalGoalsExpect) : null,
      goalRange: result.goalRange?.range || null,
      predictedScore: result.scores?.[0]?.score || null,
      scoreProbability: result.scores?.[0]?.percent ? parseFloat(result.scores[0].percent) / 100 : 0,
      consensusTag: result.fusionConsensusType || 'neutral',
      rawOutputJson: JSON.stringify(result),
    };
  }
}
```

| AI 缓存 | `server/ai_cache.json` + `doubao.js` 内联 | 持久化 + 内存 | 文件 + 内存 |

### 12.2 整合路径

蓝图的三层缓存 (L1 内存 30s / L2 文件 5min / L3 SQLite) 不是新建一套并行的缓存系统，而是**统一入口**现有缓存：

```
改造前（当前）:
  各模块独立维护自己的缓存 → 入口分散、TTL 不一致、无统一失效策略

改造后（目标）:
  请求 → cache.get('key') → L1 内存 → L2 文件 → L3 SQLite → 计算
          ↑ 所有模块通过统一接口访问，TTL 和失效由缓存层管理
```

### 12.3 整合步骤

1. **保留现有缓存实现不动**（零风险）
2. **新建 `server/core/cache-unified.js`** 提供统一 `cache.get(key, { ttl, fallback })` 接口
3. **逐步迁移**现有缓存调用点，从 `getDataJson()` → `cache.get('data.json', { ttl: 60000 })`
4. **功守道 cache.json** 作为 L2 文件缓存的第一个试点
5. **feature_store / unified_predictions** 作为 L3 SQLite 缓存的第一批 key

**重要**：不要一次性替换所有缓存调用，每次迁移一个调用点并验证 API 响应时间无劣化。

| `better-sqlite3` | 本地开发 (Windows/Node 18+) | `_initBetterSqlite3()` → `db.exec(DDL)` | 同步，所有 CREATE TABLE 在一个 exec 中 |
| `sql.js` | 生产 (CentOS 6) | `_initSqlJs()` → `adp.execDDL(DDL)` | 异步 Promise，建表在 `.then()` 回调中 |

### 13.2 蓝图新表的建表规范

**关键坑**（来自 AGENTS.md §7.6 教训）：如果只在 `_initBetterSqlite3()` 中建表而忘了 `_initSqlJs()` 的对应代码，**生产环境会缺表**。

**正确做法**——新增表必须在**两个后端**都添加：

```javascript
// 在 database.js 中新建辅助函数，避免漏加
function _initNewTables(adpOrDb) {
  // 统一接收 execDDL 或 db.exec，根据后端传入
  const execDDL = typeof adpOrDb === 'function' 
    ? adpOrDb 
    : (sql) => adpOrDb.exec(sql);

  execDDL(`
    CREATE TABLE IF NOT EXISTS unified_predictions (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      match_id TEXT NOT NULL, match_date TEXT NOT NULL,
      model_name TEXT NOT NULL, model_version TEXT NOT NULL,
      prediction_id TEXT NOT NULL,
      direction TEXT, direction_confidence REAL,
      goal_total REAL, goal_range TEXT, over_under TEXT,
      predicted_score TEXT, score_probability REAL,
      features_json TEXT, raw_output_json TEXT,
      consensus_tag TEXT, fetch_batch_id TEXT,
      computed_at TEXT DEFAULT (datetime('now','localtime')),
      UNIQUE(match_id, match_date, model_name, model_version, prediction_id)
    );
    -- ... 其余表同理
  `);
}

// better-sqlite3 后端调用
_initNewTables((sql) => db.exec(sql));

// sql.js 后端调用
adp.execDDL('...'); // 或在 _initNewTables 中统一
```

**更推荐的方案**：将所有新表的 DDL 抽取为 `NEW_TABLES_DDL` 常量字符串，两个后端共用：

```javascript
const NEW_TABLES_DDL = `
  CREATE TABLE IF NOT EXISTS unified_predictions (...);
  CREATE TABLE IF NOT EXISTS prediction_outcomes (...);
  CREATE TABLE IF NOT EXISTS feature_store (...);
  CREATE TABLE IF NOT EXISTS odds_history_v2 (...);
  CREATE TABLE IF NOT EXISTS h2h_history (...);
  CREATE TABLE IF NOT EXISTS league_standings (...);
  CREATE TABLE IF NOT EXISTS data_lineage (...);
`;

// 两个 init 函数都调用同一个常量
```

## 18. 落地实施影响评估与实施建议

> **评估结论：可以落地，无需中断现有项目运行。**

### 18.2 🟢 零风险项（纯增量，不改老代码）

| # | 操作 | 触及文件 | 为什么零风险 |
|:--:|------|------|------|
| 1 | `database.js` 新增 7 张表 DDL | `server/database.js` | `CREATE TABLE IF NOT EXISTS` 不做任何删除/ALTER，不影响现有 `matches`/`recommends`/`prediction_logs` 表。**但必须两套后端都加**（better-sqlite3 + sql.js，参照 §13.2 的教训） |
| 2 | 新建 `server/core/prediction-adapter.js` | 新文件 | 6 个 Adapter 类**只调用现有函数不修改现有模块**。例如 `GongshoudaoAdapter.predict()` 调用 `gongshoudao/index.js` 的 `computeSingleMatch()`，纯薄封装 |
| 3 | 新建 `server/core/prediction-fusion.js` | 新文件 | 全新融合管道，**平行运行**不替代现有功守道/PK/AI 输出 |
| 4 | 新建 `server/core/feature-engine.js` | 新文件 | 从已有数据源（shuju_data / 500.com / AI）计算特征写入 `feature_store`，不替换现有数据流 |
| 5 | 新建 `server/core/outcome-backfill.js` | 新文件 | 与现有 `backfillResults()` **并行运行**，各自写各自的表 |
| 6 | 新建 `server/core/data-quality.js` | 新文件 | 独立监控模块，不拦截现有数据流 |
| 7 | 新建 `scripts/fetch_h2h.js` | 新脚本 | 独立抓取脚本，不修改 `fetch_500odds.js` |
| 8 | 新建前端 `model-dashboard.js` / `data-health.js` | 新文件 | 新页面文件，**不注册路由前完全不加载** |

> 这 8 项占蓝图总工作量的 ~40%，可以一口气做完并部署，对线上零影响。

### 18.3 🟡 低风险项（需验证，但有开关保护）

#### 18.3.1 新增 API 路由 — 不碰现有路由

在 `server/index.js` 中 `switch-case` 末尾追加 4 个新路由（`prediction-fusion`、`model-dashboard`、`data-health`、`prediction-consensus`），不影响已有路由（先匹配先返回）。

**风险点**：部署时必须确保 `server/index.js` 完整上传，避免部分更新的文件不匹配 PM2 已加载的旧版本。

#### 18.3.2 `match-detail` API 增强 — 追加字段不破坏兼容

当前 API 返回：
```javascript
{ code: 1, data: { match: {...}, recommends: [...] } }
```

增强后追加 `consensus`、`features`、`h2h`、`standings` 字段。前端不读取这些新字段就完全不受影响。可以分两步走：先部署后端返回新字段 → 再部署前端使用新字段。

#### 18.3.3 `main-fusion.js` 注册新页面路由

已有模式（参照 §16.1 的教训）：
- `_ensurePage` 新增 `case 'model-dashboard'` / `case 'data-health'` 分支
- `switchTab` 新增对应分支

**风险点**：必须同步部署 `main-fusion.js`，否则旧版不识别新路由（导致空白页）。已有 `confirm-scheme` 的前车之鉴。

#### 18.3.4 `match-detail.js` 插入新区块

在现有 `goDetail()` 流程中插入新区块渲染函数（`renderConsensusBar()` 等），全部封装为独立函数，如果对应数据为空则跳过——即后端还没返回新字段时，页面行为与现在完全一致。

#### 18.3.5 `data_sync.js` 新增积分榜同步

在现有 `data_sync.js` 的 `backfillResults()` 之后追加积分榜抓取调用。不修改现有调度逻辑。

### 18.4 🟠 需准备项（第 3-4 周，需要过渡期）

#### 18.4.1 `odds_history` JSON → `odds_history_v2` 表迁移

**这是蓝图中对现有系统最敏感的一项改造**，因为 `odds_history` 被以下模块消费：

| 消费者 | 文件 | 影响 |
|--------|------|------|
| `match-odds` API | `server/index.js:1084` | 功守道弹窗赔率数据 |
| 功守道 `market.js` | `server/gongshoudao/market.js` | 赔率变化分析 |
| `odds-tracker.js` | `server/core/odds-tracker.js` | 赔率走势追踪 |

**推荐策略**：双读过渡——API 层同时查 JSON 文件和 SQLite 表，优先读新表，fallback 读旧 JSON。积累足够数据（至少 2 周）后切换。

#### 18.4.2 `match-detail` API 消费者兼容

除了 Web 前端，还要确认小程序端（`miniprogram/pages/match-detail/`）和 `preview/app.js` 是否兼容新字段——它们只取 `detail.match` 对象中的已知字段，追加新字段不会影响。

### 18.5 🔴 暂缓项（积累数据后才能切换）

- **`prediction_logs` 逐步废弃**：必须等 `unified_predictions` + `prediction_outcomes` 积累 ≥ 2 周数据、动态权重稳定后（蓝图 §11.2 第四阶段，约第 8 周）。

### 18.6 部署风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|------|:--:|:--:|------|
| `database.js` 生产端（sql.js）缺新表 | 🟡 中 | 🔴 高 | 两个后端各自验证 CREATE TABLE（蓝图 §13.3 checklist） |
| `server/core/` 依赖遗漏导致 500 | 🟡 中 | 🔴 高 | 部署前 `node -e` 扫描依赖链 |
| `main-fusion.js` 路由遗漏导致新页面空白 | 🟡 中 | 🟡 中 | 部署后浏览器验证所有新标签 |
| 新模块拖慢 API 响应 | 🟢 低 | 🟡 中 | 功能开关默认关闭 + 并行运行 |
| `prediction_logs` 数据断裂 | 🟢 低 | 🔴 高 | 双写 ≥ 2 周 |

### 18.7 推荐落地时间线

```
第 1 天（立即，零风险纯增量，部署一次）:
  ├── database.js: 新增 7 张表 DDL（两套后端）
  ├── server/core/: 新建 6 个模块文件

  ├── preview/js/pages/: 新建 model-dashboard.js + data-health.js

第 3-5 天（低风险，功能开关保护）:

  ├── preview/js/main-fusion.js: 注册新页面路由
  └── 部署 + 浏览器验证新页面可访问

第 6-10 天（核心，平行运行）:
  ├── match-detail.js: 逐步插入新区块（共识条→战绩→H2H→排名）
  ├── data_sync.js: 积分榜同步 + 回填触发融合引擎
  └── 开启 UNIFIED_PREDICTIONS 功能开关（灰度）

第 3-4 周（过渡期）:
  ├── odds_history 双读迁移
  └── 积累 outcomes 数据

第 5+ 周:
  └── prediction_logs 迁移收尾
```

### 18.8 关键保障措施小结

| 保障 | 机制 | 说明 |

### 18.9 总结

蓝图的 **40% 可以立即落地（纯增量，零风险）**，**30% 可以低风险落地（有开关保护）**，真正需要等待的只有 `prediction_logs` 废弃这一项（约 2 个月后）。

每个阶段都设计了独立的部署包和验证步骤，确保不中断现有项目运行。所有改动都在功能开关保护下进行，出问题一行配置即可回退。
