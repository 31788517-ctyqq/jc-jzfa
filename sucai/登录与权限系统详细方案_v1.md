# 登录与权限系统详细方案 v1（目录级）

> 文档状态：`规划版`（仅方案，不含代码实现）  
> 适用范围：`JC-ZJFA` 前端 `preview` + 后端 `server/index.js (POST /api + action)` 架构  
> 目标：建立“仅预置账号可登录、可改密、关键模块可权限控制”的可扩展体系

---

## 1. 背景与目标

### 1.1 背景

当前系统为单入口 SPA（`switchTab` 页面态）+ 后端 `POST /api` 的 `action` 分发模型，尚未形成统一账号认证与权限控制边界。随着“方案、回测、模型看板、数据健康”等关键模块上线，需要将访问控制前置为平台能力。

### 1.2 本期目标（v1）

- 禁止用户注册，仅允许**系统预置账号**登录。
- 支持用户**修改本人密码**。
- 建立可扩展的权限模型（RBAC），优先覆盖关键模块。
- 在后端形成统一鉴权/鉴权失败返回规范（401/403）。
- 先输出完整方案与目录，不在本期文档中包含代码。

### 1.3 非目标（v1 不做）

- 第三方登录（微信、OAuth、SSO）。
- 多组织租户隔离。
- 复杂 ABAC 策略引擎。
- MFA（双因子）与风控画像（可列入 v2）。

---

## 2. 设计原则

- **后端鉴权优先**：前端隐藏仅为体验，安全边界在后端。
- **最小权限原则**：默认拒绝，按角色放行。
- **兼容现有 action 架构**：不重构路由模式，先在 action 层做权限拦截。
- **可审计**：关键登录与高风险操作必须留痕。
- **可灰度**：权限可先覆盖高风险 action，再逐步扩展。

---

## 3. 总体架构（目录级）

### 3.1 模块拆分

1. **认证模块（Auth）**
   - 登录、登出、会话校验、改密。
2. **账号模块（User）**
   - 账号状态、强制改密、密码策略。
3. **授权模块（RBAC）**
   - 角色、权限点、用户-角色绑定。
4. **审计模块（Audit）**
   - 登录日志、权限拒绝日志、关键操作日志。
5. **接入层（Policy Guard）**
   - 在 `POST /api` action 分发前执行：身份识别 → 权限判定 → 放行/拒绝。

### 3.2 建议目录（仅规划）

- `server/auth/`
  - `auth-service.js`（登录/登出/改密）
  - `session-service.js`（会话签发/校验/失效）
  - `rbac-service.js`（权限计算）
  - `policy-map.js`（action -> permission 映射）
  - `audit-service.js`（审计写入）
- `server/tests/auth/`
  - `auth-contract.test.js`
  - `rbac-contract.test.js`
  - `policy-guard.test.js`
- `preview/js/pages/`
  - `login.js`
  - `account-security.js`
- `preview/js/`
  - `auth-client.js`
  - `auth-guard.js`

## 4. 接口清单（v1 草案）

> 统一风格：`POST /api`，通过 `action` 区分。  
> 响应规范建议：
> - 成功：`{ code: 1, data, msg? }`
> - 未认证：`{ code: 401, msg: 'UNAUTHORIZED' }`
> - 无权限：`{ code: 403, msg: 'FORBIDDEN' }`
> - 业务失败：`{ code: 0, msg }`

### 4.1 认证接口

1. `action: 'auth-login'`
   - **用途**：账号密码登录（仅预置账号）。
   - **请求**：`{ username, password }`
   - **返回**：`{ user, roles, mustChangePassword, sessionMeta }`
   - **规则**：账号禁用/锁定时拒绝。

2. `action: 'auth-logout'`
   - **用途**：主动退出并失效当前会话。
   - **请求**：`{}`
   - **返回**：`{ ok: true }`

3. `action: 'auth-session'`
   - **用途**：获取当前会话身份与权限摘要（页面刷新恢复态）。
   - **请求**：`{}`
   - **返回**：`{ user, roles, permissionsDigest }`

### 4.2 密码管理接口

4. `action: 'auth-change-password'`
   - **用途**：用户修改本人密码。
   - **请求**：`{ oldPassword, newPassword }`
   - **返回**：`{ ok: true, needRelogin?: boolean }`
   - **规则**：校验旧密码；满足复杂度策略。

5. `action: 'auth-force-reset-password'`（管理员能力，v1 可预留）
   - **用途**：重置目标账号密码并标记强制改密。
   - **请求**：`{ userId }`
   - **返回**：`{ tempPassword, mustChangePassword: true }`

### 4.3 账号与权限管理接口（v1 管理端预留）

6. `action: 'user-list'`
   - **用途**：账号列表与状态查看。

7. `action: 'user-create'`
   - **用途**：系统生成账号（无注册）。

8. `action: 'user-update-status'`
   - **用途**：启用/禁用/解锁账号。

9. `action: 'role-list'`
   - **用途**：角色列表。

10. `action: 'role-permission-update'`
    - **用途**：调整角色权限。

11. `action: 'user-role-update'`
    - **用途**：给用户绑定角色。

### 4.4 与现有 action 的权限接入（重点）

按当前 `api-contract` 动作矩阵，建议首批接入：

- 高风险优先：
  - `my-plan-save`、`my-plan-delete`
  - `sync-match-date`、`sync-gov-schedule`
  - `backfill-results`、`auto-heal`、`refill-expert-consensus`
- 关键分析：
  - `prediction-backtest`、`model-dashboard`、`data-health`、`experiment-compare`
- 可读但敏感：
  - `batch-consensus`、`pk-version-compare`、`daily-profit-7d`

## 5. 数据表草案（SQLite）

> 说明：遵循当前项目 DB 管理规范，最终由 `database.js` 统一纳管与持久化。

### 5.1 `users`（账号表）

- `id` INTEGER PK
- `username` TEXT UNIQUE NOT NULL
- `password_hash` TEXT NOT NULL
- `status` TEXT NOT NULL DEFAULT 'active'  
  值域：`active | disabled | locked`
- `must_change_password` INTEGER NOT NULL DEFAULT 1
- `last_login_at` TEXT NULL
- `password_updated_at` TEXT NULL
- `failed_login_count` INTEGER NOT NULL DEFAULT 0
- `locked_until` TEXT NULL
- `created_at` TEXT NOT NULL
- `updated_at` TEXT NOT NULL

索引建议：
- `idx_users_username (username)`
- `idx_users_status (status)`

### 5.2 `roles`（角色表）

- `id` INTEGER PK
- `code` TEXT UNIQUE NOT NULL  
  如：`super_admin` `ops_admin` `analyst` `viewer`
- `name` TEXT NOT NULL
- `description` TEXT NULL
- `is_builtin` INTEGER NOT NULL DEFAULT 1
- `created_at` TEXT NOT NULL
- `updated_at` TEXT NOT NULL

### 5.3 `permissions`（权限点字典表）

- `id` INTEGER PK
- `code` TEXT UNIQUE NOT NULL  
  规则：`module:action`（如 `plan:save`）
- `module` TEXT NOT NULL
- `action` TEXT NOT NULL
- `risk_level` TEXT NOT NULL DEFAULT 'medium'  
  值域：`low | medium | high | critical`
- `description` TEXT NULL
- `created_at` TEXT NOT NULL

索引建议：
- `idx_permissions_module (module)`
- `idx_permissions_risk_level (risk_level)`

### 5.4 `role_permissions`（角色-权限关联）

- `role_id` INTEGER NOT NULL
- `permission_id` INTEGER NOT NULL
- `created_at` TEXT NOT NULL
- 复合唯一：`UNIQUE(role_id, permission_id)`

### 5.5 `user_roles`（用户-角色关联）

- `user_id` INTEGER NOT NULL
- `role_id` INTEGER NOT NULL
- `created_at` TEXT NOT NULL
- 复合唯一：`UNIQUE(user_id, role_id)`

### 5.6 `auth_sessions`（会话表）

- `id` INTEGER PK
- `user_id` INTEGER NOT NULL
- `session_token_hash` TEXT UNIQUE NOT NULL
- `issued_at` TEXT NOT NULL
- `expires_at` TEXT NOT NULL
- `revoked_at` TEXT NULL
- `ip` TEXT NULL
- `user_agent` TEXT NULL
- `last_seen_at` TEXT NULL

索引建议：
- `idx_auth_sessions_user_id (user_id)`
- `idx_auth_sessions_expires_at (expires_at)`

### 5.7 `audit_logs`（审计日志表）

- `id` INTEGER PK
- `actor_user_id` INTEGER NULL
- `event_type` TEXT NOT NULL  
  如：`login_success` `login_failed` `password_changed` `permission_denied` `admin_user_created`
- `target_type` TEXT NULL
- `target_id` TEXT NULL
- `detail_json` TEXT NULL
- `ip` TEXT NULL
- `user_agent` TEXT NULL
- `created_at` TEXT NOT NULL

索引建议：
- `idx_audit_logs_event_type (event_type)`
- `idx_audit_logs_actor_user_id (actor_user_id)`
- `idx_audit_logs_created_at (created_at)`

## 6. 权限点字典（v1）

### 6.1 命名规范

- 格式：`module:action`
- 示例：`auth:login`、`plan:save`、`backtest:view`
- 规则：可读动作与后端 action 映射解耦，便于未来 API 重构

### 6.2 核心权限点（建议首批）

#### A. 认证与账号

- `auth:login`
- `auth:logout`
- `auth:change_password`
- `user:view`
- `user:create`
- `user:disable`
- `user:unlock`
- `user:force_reset_password`

#### B. 角色与授权

- `role:view`
- `role:assign`
- `role:permission_manage`

#### C. 方案模块

- `plan:view`
- `plan:save`（映射 `my-plan-save`）
- `plan:delete`（映射 `my-plan-delete`）
- `plan:share`
- `plan:confirm`

#### D. 回测与模型

- `backtest:view`（映射 `prediction-backtest`）
- `dashboard:model_view`（映射 `model-dashboard`）
- `dashboard:data_health_view`（映射 `data-health`）
- `dashboard:experiment_compare`（映射 `experiment-compare`）

#### E. 功守道与版本洞察

- `gs:view`（映射 `gongshoudao` / `gongshoudao-all`）
- `insight:batch_consensus`（映射 `batch-consensus`）
- `insight:pk_compare`（映射 `pk-version-compare`）

#### F. 同步与运维高风险

- `ops:sync_match_date`（映射 `sync-match-date`）
- `ops:sync_gov_schedule`（映射 `sync-gov-schedule`）
- `ops:backfill`（映射 `backfill-results`）
- `ops:auto_heal`（映射 `auto-heal`）
- `ops:refill_consensus`（映射 `refill-expert-consensus`）

### 6.3 角色建议（v1）

- `super_admin`：全部权限
- `ops_admin`：含运维/同步/回填，不含角色权限管理（可按组织策略决定）
- `analyst`：可看回测、看板、排行、方案查看，不可执行运维类写操作
- `viewer`：只读浏览（基础页面 + 安全只读 action）

## 7. 页面交互稿（文字线框）

## 7.1 页面清单（新增）

1. `登录页`（`login`）
2. `账号安全页`（`account-security`，改密）
3. `无权限页`（`403`）
4. `会话失效提示`（`401` 全局弹层/跳转）
5. （可选）`账号与角色管理页`（管理端）

### 7.2 登录页交互

- 输入：账号、密码
- 按钮：登录
- 状态：
  - 登录中（禁用按钮）
  - 登录失败提示（账号/密码错误、账号禁用、锁定剩余时间）
- 成功：
  - 若 `mustChangePassword=true`，强制跳转改密页
  - 否则跳转最近访问页或首页

### 7.3 改密页交互

- 输入：旧密码、新密码、确认新密码
- 校验：
  - 新密码复杂度
  - 与旧密码不能相同
  - 两次输入一致
- 成功：
  - 提示“密码修改成功”
  - 可配置“是否强制重新登录”

### 7.4 页面级权限反馈

- 无权限菜单不展示（前端体验层）
- 直达受限页面时：
  - 页面级提示：`无访问权限`
  - 提供返回首页按钮
- API 返回 403：
  - 统一 toast + 记录审计 `permission_denied`

### 7.5 与现有页面映射建议（首批）

基于当前 `switchTab` 页面：

- `plan` / `scheme` / `confirm-scheme`：挂接 `plan:*`
- `backtest`：挂接 `backtest:view`
- `model-dashboard`：挂接 `dashboard:model_view`
- `data-health`：挂接 `dashboard:data_health_view`
- `home/match/rank/hit/filter/income/quant-rank`：按角色逐步放开只读访问

## 8. 鉴权接入策略（后端）

### 8.1 接入点

在 `POST /api` 进入 `switch(action)` 前增加统一流程：

1. 解析会话（cookie/token）
2. 识别 `user + roles`
3. 根据 `action -> permission` 映射判定
4. 拒绝：401/403；放行：进入既有业务逻辑

### 8.2 action 映射策略

- 建立 `policy-map`：
  - `action` → `permission code`
- 未映射 action 默认策略：
  - v1 建议采用“白名单放行 + 逐步收敛”或“默认拒绝（仅内网管理）”之一
- 建议优先给以下动作强制权限：
  - `my-plan-save` `my-plan-delete` `sync-match-date` `sync-gov-schedule` `backfill-results` `auto-heal`

### 8.3 错误码与前端约定

- `401`：会话失效/未登录 → 跳登录页
- `403`：已登录但无权限 → 展示无权限提示
- `0`：保留原业务失败语义

## 9. 安全策略草案

- 密码仅存储哈希，不落明文。
- 登录失败计数与锁定窗口（例如 5 次失败锁 15 分钟）。
- 会话设置过期时间、支持主动吊销。
- 敏感操作写审计日志。
- 接口限流：登录接口额外加严（IP+账号双维度）。

## 10. 测试与验收口径（规划）

### 10.1 功能验收

- 无注册入口，仅管理员可创建账号。
- 预置账号可登录，禁用账号不可登录。
- 用户可修改本人密码。
- 首批关键 action 权限生效（401/403 正确返回）。

### 10.2 安全验收

- 弱口令不可通过策略。
- 暴力破解触发锁定。
- 无权限用户无法绕过前端直接调用高风险 action。

### 10.3 回归验收

- 现有核心只读 action 不被误伤（`match-list`、`ranking-list`、`match-detail` 等）。
- 方案链路（`scheme -> confirm-scheme -> my-plan-save`）权限判定准确。

## 12. 风险与决策项

### 12.1 待决策

- 会话机制：`HttpOnly Cookie` vs `Bearer Token`（建议 v1 先 Cookie）。
- 角色模型：单角色 or 多角色（建议支持多角色，先单角色使用）。
- 未映射 action 默认策略：默认拒绝 or 默认放行。

### 12.2 主要风险

- action 覆盖不完整导致“有洞”或“误拦截”。
- 前后端权限点命名不一致导致页面行为异常。
- 历史脚本/批处理调用未携带会话造成兼容问题。
