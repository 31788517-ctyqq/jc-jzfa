# 版本戳策略评审稿（1页）V1.0

> 状态：评审稿（仅文档，不改代码）  
> 目标：彻底消除 `?v=unknown`，建立可追溯、可观测、可回滚的版本戳策略  
> 适用范围：`index.html`、`preview/index.html`、`/dist` 资源、部署日志、线上核验

---

## 一、问题定义

当前部署日志出现 `★ V12: 自动版本戳 ?v=unknown`，说明版本来源解析存在不确定性。其风险包括：

- 资源缓存失效策略不可控；
- 发布内容无法快速溯源；
- 灰度/回滚时难以确认“线上到底是哪个版本”。

**评审目标**：任何部署场景下，版本戳均必须是“有意义且可追溯”的值，禁止出现 `unknown`。

---

## 二、字段定义（统一口径）

- **versionStamp**（主字段）：用于 `?v=` 注入与页面元信息展示的统一版本值。
- **versionSource**（来源字段）：记录版本戳来源类型（`git_clean` / `git_dirty` / `build_time`）。
- **buildTime**（辅助字段）：构建时间戳，格式建议 `YYYYMMDD_HHmmss`。
- **isDirty**（辅助字段）：当前工作区是否有未提交改动（布尔）。

> 约束：所有入口页面与资源注入必须共享同一个 `versionStamp`，不得各自计算。

---

## 三、优先级策略（三级降级，永不 unknown）

### P1（首选）
- 条件：可获取 Git 提交号且工作区干净。
- 结果：`versionStamp = <shortHash>`（例：`ec8dccb8`）
- `versionSource = git_clean`

### P2（次选）
- 条件：可获取 Git 提交号但工作区有改动。
- 结果：`versionStamp = <shortHash>-dirty`（例：`ec8dccb8-dirty`）
- `versionSource = git_dirty`

### P3（兜底）
- 条件：Git 不可用（无 `.git`、命令失败、浅环境等）。
- 结果：`versionStamp = <buildTime>`（例：`20260619_2101`）
- `versionSource = build_time`

**硬规则**：任一场景均不得输出 `unknown`。

---

## 四、异常场景与处理

1. **Git 不可访问/命令失败**  
   - 处理：立即降级到 `buildTime`，并在日志标记 `versionSource=build_time`。

2. **工作区大量未提交改动**  
   - 处理：使用 `shortHash-dirty`，明确区分“提交版”与“现场热修版”。

3. **多入口注入不一致（root/preview/dist）**  
   - 处理：部署时只生成一次 `versionStamp`，各入口共享引用。

4. **部署成功但前端仍旧资源**  
   - 处理：核查页面中的 `?v=` 与部署日志输出是否一致；如不一致，按缓存链路排查（浏览器/Nginx/SW）。

5. **回滚后版本识别混乱**  
   - 处理：回滚也必须生成并打印新 `versionStamp`，禁止沿用旧日志描述。

---

## 五、验收清单（评审通过标准）

- [ ] 部署日志中不再出现 `?v=unknown`。  
- [ ] 日志可同时看到 `versionStamp` 与 `versionSource`。  
- [ ] `index`、`preview`、`dist` 三处版本戳一致。  
- [ ] dirty 部署可区分（带 `-dirty` 后缀）。  
- [ ] 无 Git 环境仍可产出有效版本戳（`buildTime`）。  
- [ ] 线上抽检可通过页面资源 URL 快速确认当前版本。  
- [ ] 回滚后可在日志与页面中识别新旧版本差异。

---

## 六、发布与治理建议

- **发布前**：在 dry-run 输出本次将使用的 `versionStamp` 与来源。  
- **发布后**：验证脚本增加“版本戳一致性”检查项（root/preview/dist）。  
- **长期治理**：将“禁止 unknown”纳入 pre-deploy 检查，作为阻断项。
