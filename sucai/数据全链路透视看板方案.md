## 1. 当前现状与核心问题

### 1.1 已有监控资产（已存在）

| 模块 | 层级 | 覆盖维度 |
|------|------|----------|
| `data-quality.js` | 抓取层 | 抓取成功率门禁(≥90%)、完整性门禁(≥85%)、赔率突变检测(>30%) |
| `data-auditor.js` | 存储层 | 6大类18项核查（比赛完整性/推荐一致性/方案一致性/赔率完整性/DB一致性/跨源一致性） |
| `ingestion-guard.js` | 摄入层 | 半场误判检测、比分单调性、matchStatus锁定规则 |
| `result-verifier.js` | 赛果层 | 多源(3+)交叉投票对账 |
| `score-corrector.js` | 修正层 | sporttery官方赛果优先 + detail.php备降 |
| `alert-monitor.js` | 告警层 | P0~P1 三级告警、自愈闭环 |
| `db-metrics.js` | DB层 | SQLite写入成功率统计 |
| `file-tracker.js` | 文件层 | 关键文件存在性/大小/新鲜度/快速指纹 |
| `health.js` | 总览层 | 10项深度健康检查 |
| `resource-monitor.js` | 资源层 | CPU/内存/事件循环延迟 |
| `data-health.js` (前端) | 展示层 | 数据源抓取率+完整性+告警+门禁状态 |
| `model-dashboard.js` (前端) | 展示层 | 模型命中率排行+趋势+联赛热力图 |
| 管理后台系统Tab | 展示层 | 服务状态/管线健康/运维操作/最近错误 |

### 1.2 关键缺口（靠"猜"的环节）

| 缺口 | 具体问题 | 严重度 |
|------|----------|:------:|
| **G-1 抓取到手但没落盘** | 爬虫返回200但数据未写入data.json / odds_history | P0 |
| **G-2 抓取覆盖率不可见** | 当天哪些比赛已抓/未抓/缺哪些字段，无实时统计 | P0 |
| **G-3 渲染正确性无监控** | API返回数据→前端渲染结果，无自动化校验 | P1 |
| **G-4 计算管线孤立** | 预测生成→融合→回填各环节耗时/成功率/差异无统一视图 | P1 |
| **G-5 展示对比缺失** | 用户看到的 vs 预期应看到的数据，无快照对比机制 | P1 |
| **G-6 历史趋势退化** | 某数据源连续3天成功率下降/完整性恶化，无趋势图 | P2 |
| **G-7 跨源对账不直观** | result-verifier有交叉验证但结果只有日志，无可视化 | P2 |
| **G-8 数据新鲜度无明细** | 只知道"data.json 120分钟前更新"，不知具体哪条数据过期 | P2 |

## 2. 全链路数据管道模型

定义标准化的数据阶段划分，每个阶段定义**入口**、**出口**、**质量指标**、**监控点**：

```
阶段1              阶段2              阶段3              阶段4              阶段5
抓取(Scrape)  →    落盘(Ingest)   →    计算(Compute)  →    服务(Serve)    →    展示(Display)
┌──────────┐      ┌───────────┐       ┌───────────┐       ┌───────────┐       ┌───────────┐
│500.com   │      │data.json  │       │prediction │       │api-cache  │       │前端页面    │
│midou310  │ ──→  │odds_hist. │ ──→   │-fusion    │ ──→   │Redis      │ ──→  │SW缓存     │
│sporttery │      │DB tables  │       │plan-gen   │       │响应缓存   │       │用户浏览器  │
│deepseek  │      │sporttery_ │       │pk_scorer  │       │           │       │           │
│豆包      │      │archive    │       │backfill   │       │           │       │           │
└──────────┘      └───────────┘       └───────────┘       └───────────┘       └───────────┘
    ↓监控              ↓监控               ↓监控               ↓监控               ↓监控
  HTTP状态码         文件/DB写入       管线执行率         缓存命中率         渲染差异率
  响应耗时           完整性比率        模型产出量         响应耗时           DOM快照对比
  数据条数           跨源一致性        回填成功率         TTFB/首字节       截图对比
```

### 2.1 阶段定义与指标矩阵

| # | 阶段 | 入口 | 出口 | 关键质量指标 (KQI) |
|---|------|------|------|-------------------|
| S1 | **抓取** | 外部API endpoint | 原始响应JSON | HTTP成功率、响应耗时、返回条数 vs 预期条数、新数据比例 |
| I1 | **落盘** | 原始响应JSON | data.json / odds_history / DB | 写入成功率、文件/DB大小变化量、字段完整性、时间戳新鲜度 |
| C1 | **计算** | data.json / DB原始数据 | predictions / plans / scores | 管线执行耗时、产出记录数、空产出率、回填覆盖率 |
| S2 | **服务** | 计算产出数据 | API响应JSON | 缓存命中率、API成功率、响应耗时P50/P95、错误率 |
| D1 | **展示** | API响应JSON | 用户可见DOM | 页面渲染耗时、JS异常率、数据空值率、用户反馈 |

|------|-----------|--------|

### 3.3 数据看板 Tab 结构（管理后台）

当前管理后台有4个Tab：用户 / 订阅 / 返利 / 系统。规划新增 **3个数据类Tab**，调整为7个Tab：

```
[用户] [订阅] [返利] [系统] [📥 数据采集] [⚙️ 数据计算] [📊 质量总览]
                              (Tab 5)       (Tab 6)       (Tab 7)
```

**系统Tab保持不变**，作为运维操作入口 + 快速状态一览。
**数据采集Tab** 从系统Tab中拆出并大幅增强。
**数据计算Tab** 全新。
**质量总览Tab** 作为7天/30天趋势的Dashboard首页。

#### 4.4.3 渲染差异检测（前端的"自拍"机制）

```html
<!-- 比赛列表的赔率区域 -->
<div data-snapshot="odds-周三001" data-expected='{"spf":["1.85","3.40","3.60"]}'>
  ...渲染后的赔率行...
</div>
```

实现方式: 轻量级checker函数，不引入额外依赖:
```javascript
function checkSnapshot(el) {
  const snapshotId = el.dataset.snapshot;
  if (!snapshotId) return;
  const expected = el.dataset.expected;
  if (!expected) return;
  // 序列化实际渲染的赔率值
  const actual = serializeOdds(el);
  if (actual !== expected) {
    console.warn(`[渲染差异] ${snapshotId}: 预期=${expected}, 实际=${actual}`);
    // 可选: 上报到后端
  }
}
```

## 5. 后端新增服务端模块与改造

### 5.1 新增模块: data-pipeline-monitor.js

**位置**: `server/core/data-pipeline-monitor.js`

**职责**: 统一采集各阶段指标，聚合为前端看板所需的数据结构。串联现有各分散monitor的数据。

```javascript
class DataPipelineMonitor {
  constructor() {
    this.metrics = {
      scrape: {},   // 抓取指标
      ingest: {},   // 落盘指标
      compute: {},  // 计算指标
      serve: {},    // 服务指标
    };
  }

  // — 抓取阶段 —
  recordScrape(source, result) { /* 记录抓取结果 */ }
  
  // — 落盘阶段 —
  recordIngest(type, success) { /* 记录写入结果 */ }
  
  // — 计算阶段 —
  recordComputeStage(stageName, duration, output) { /* 记录管线阶段耗时 */ }
  
  // — 展示阶段 —
  recordRenderCheck(pageId, snapshotId, pass) { /* 记录渲染检测结果 */ }

  // — 聚合 —
  getPipelineDashboard(days) { /* 聚合所有指标 */ }
  getComputeDashboard(days) { /* 聚合计算管线指标 */ }
  getQualityScore(days) { /* 计算综合质量评分 */ }
}
```

**评分算法**:

```
综合质量评分 = 
  w1 × 抓取成功率(0-100) +
  w2 × 存储完整性(0-100) +
  w3 × 计算成功率(0-100) +
  w4 × 服务可用率(0-100) +
  w5 × 展示正确率(0-100)

其中 w1=0.25, w2=0.25, w3=0.20, w4=0.15, w5=0.15
```

各维度分:
- **抓取**: min(100, 各源成功率加权平均 × 100)
- **存储**: min(100, 完整性比率 × 写入成功率 × 100)
- **计算**: min(100, 管线成功率 × 回填覆盖率 × 100)
- **服务**: min(100, 缓存命中率 × API成功率 × 100)
- **展示**: min(100, 渲染检测通过率 × 页面加载成功率 × 100)

## 8. 关键设计决策

### 8.1 为什么不在现有data-health.js上直接扩展?

当前 `data-health.js` 设计为单一页面，API仅返回抓取成功率+完整性+告警。如在其上堆积计算管线+跨源对账+趋势图，会导致:
1. 单个API响应膨胀 (当前~3KB → 预期~50KB)
2. 前端加载过重 (当前~330行 → 预期~1500行)
3. 性能退化 (混在一起请求有依赖的数据)

**决策**: 拆分为3个独立Tab + 3个独立前端模块，每个模块有专注的API端点和数据范围。

### 8.2 质量评分怎么算？

5维度加权评分，权重可配置:

```javascript
const QUALITY_WEIGHTS = {
  scrape: 0.25,   // 抓取
  storage: 0.25,  // 存储
  compute: 0.20,  // 计算
  serve: 0.15,    // 服务
  display: 0.15,  // 展示
};

const GATE_THRESHOLDS = {
  scrape: 0.90,   // 抓取门禁
  storage: 0.85,  // 存储门禁
  compute: 0.80,  // 计算门禁 (AI 预测偏低是可接受的)
  serve: 0.95,    // 服务门禁
  display: 0.85,  // 展示门禁
};
```

评分阈值举例:
- **≥95**: 优秀 (绿色) — 无需关注
- **85-94**: 良好 (蓝色) — 常规监控
- **70-84**: 一般 (橙色) — 关注异常
- **<70**: 差 (红色) — 需人工介入

### 8.3 渲染快照机制不引入E2E测试框架

E2E (Playwright) 用于开发验证，不适合生产环境实时监控。生产环境渲染检测策略:
- 轻量级: 纯前端JS，无外部依赖
- 仅检测关键数据区 (赔率值、比分、状态等)，不检测样式
- 异步上报 (不阻塞用户交互)
- 采样率: 1/10 页面访问 (减少后端压力)

## 9. 风险和注意事项

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 埋点过多拖慢核心流程 | 抓取/计算性能下降 | 埋点采用异步fire-and-forget，不用同步await |
| API响应体过大 | 移动端流量/渲染压力 | `pipeline-dashboard` 默认只返回24h数据，支持days参数控制 |
| 内存占用 (进程内Map) | 长期运行内存泄漏 | 数据每24h自动清理，设置上限(10万条)后丢弃最旧 |
| 前端新页面初始加载慢 | 用户体验差 | 使用page-skeleton骨架屏 + 懒加载waterfall |
| 数据冲突: 跨源对账公示后用户质疑 | 信任危机 | 置信度标签只在前端展示有3票验证的"高"置信度，矛盾项仅管理员可见 |
